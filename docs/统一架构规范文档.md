## 1. 命名规范



命名根取自计划书标题「**AI管家 Agent 生态体系**」。唯一真值源：`ai_butler/core/naming.py`。



| 标识 | 取值 | 派生自 |

|---|---|---|

| ROOT | `ai-butler` | 标题「AI管家」 |

| ECOSYSTEM | `ai-butler-ecosystem` | 标题「AI管家 **Agent 生态体系**」 |

| PACKAGE | `ai_butler` | ROOT 下划线形式 |

| ENV_PREFIX | `AIBUTLER_` | 应用级环境变量前缀 |

| DB_NAME | `ai_butler` | 与包名一致 |

`middleware`（中间件）/ `agent_wiki`（Agent-Wiki）。



**可调整**：改 `naming.py` 或设 `AIBUTLER_ROOT` / `AIBUTLER_ECOSYSTEM` /

`AIBUTLER_NAMESPACE` 即可，业务代码零改动。由 `tests/test_naming.py` 强制。



**可复用**：垂类走 `vertical_key("travel", ...)`——计划书五要求点餐、售后等垂类复用同一套结构，

因此**新增垂类不新增命名规则**。

## 5. 四环境隔离体系



计划书：三、P0-1「搭建四环境隔离体系：开发、测试、预发布、生产完全独立隔离」



**隔离口径**：四环境之间**不共享任何资源**——宿主端口、数据库名、数据目录、容器名、

项目名、配置与密钥文件两两不相交。真值源 `ai_butler/core/environments.py`。



| 环境 | PG 端口 | Redis 端口 | API 端口 | 数据库 | 数据目录 | 宿主端口 |

|---|---|---|---|---|---|---|

| dev | 5434 | 6381 | 8400 | aibutler_dev | data/dev | 发布 |

| test | 5435 | 6382 | 8401 | aibutler_test | data/test | 发布 |

| staging | 5436 | 6383 | 8402 | aibutler_staging | data/staging | **不发布** |

| prod | 5437 | 6384 | 8403 | aibutler_prod | data/prod | **不发布** |



**运行时守卫**：`server.build_app()` 启动前调用 `validate_runtime()`，

校验当前进程所连资源属于它声明的环境，防止「用开发配置连上生产库」。缺失或串用即拒绝启动。



**密钥隔离**：`.env.dev / .test / .staging / .prod` 各自持有独立的

`SESSION_TOKEN_SECRET` / `FIELD_ENCRYPTION_KEY` / `POSTGRES_PASSWORD`；

**预发布与生产不得复用开发的外部凭据**（凭据字段留空，由运维另配）。



**启动**：



```bash

# 本地（dev / test）——叠加端口文件

docker compose -f deploy/compose/base.yml -f deploy/compose/local-ports.yml --env-file .env.dev up -d



# 预发布 / 生产——不叠加端口文件，数据面只在 internal 网络内可达

docker compose -f deploy/compose/base.yml --env-file .env.prod up -d

```

## 6. 三层网络隔离



计划书：三、P0-1「三层网络隔离：外网业务层、内网服务层、沙箱隔离层」



| 分区 | 定义 | 成员 |

|---|---|---|

| `edge` | 外网业务层：唯一对外可达 | api |

| `internal` | 内网服务层：数据面只在此层 | postgres、redis |

| `sandbox` | 沙箱隔离层：离线进化链路执行环境 | harness（P10） |



**硬规则**：



1. 数据面服务**只能**挂 `internal`，不得挂 `edge` 或 `sandbox`；

2. **任何环境**下 `sandbox` 都必须 `internal: true`；

3. 沙箱服务不得与 `internal` 共享成员，确保沙箱内代码执行够不到用户私有数据；

4. 严格内网模式下数据面**不得发布宿主端口**。



**本地环境的唯一让渡**：模板把内网服务层的 `internal` 写成环境驱动

`internal: ${DATA_PLANE_INTERNAL:-true}`——预发布/生产为 true，本地 dev/test 为 false。

原因是 Docker **不会**为只挂 `internal` 网络的容器完成端口转发（对照实验见 MEMORY.md E-07），

而本地开发需要宿主可达数据面。**沙箱隔离层不受该开关影响，始终严格。**



以上四条均由 `tests/test_network_zones.py` 静态校验，防止后续改动悄悄破坏隔离。

## 7. 中间件装配顺序



```text

RequestLogMiddleware → TimeoutMiddleware → SessionAuthMiddleware → 业务路由

```



顺序不可颠倒：



- **RequestLog 最外层**，才能读到内层 SessionAuth 写入的 `scope["state"]["user_id"]`（计划书要求保留 user_id 排障）；

- **Timeout 在 SessionAuth 之外**，使「会话校验自身卡住」也受超时保护；

- **SessionAuth 紧贴业务**，未通过校验的请求绝不进入业务路由（计划书七、11）。



超时采用**首字节截止**语义：响应已开始则解除截止，否则会切断流式转发（计划书三、P7）。

该顺序由 `tests/test_app.py` 端到端断言，不靠注释保证。

## 12. Git 分支规范与 CI 流水线



计划书：三、P0-2「制定 Git 分支规范、CI 自动构建、自动部署流水线」



### 12.1 分支模型



| 分支 | 用途 | 合并去向 |

|---|---|---|

| `main` | 生产就绪，只接受 `release/*` 与 `hotfix/*` 合并 | — |

| `develop` | 集成分支，功能汇入 | `release/*` |

| `feature/*` | 单个功能或单个 Agent | `develop` |

| `release/*` | 发布候选，冻结新功能 | `main` + `develop` |

| `hotfix/*` | 生产缺陷紧急修复 | `main` + `develop` |



约定：一个 Agent 一个 `feature/*`（计划书三、P4「逐个开发、逐个单测、逐个上线」）；

合并前必须全量测试通过。



### 12.2 CI（`.github/workflows/ci.yml`）



平台选型 **Gitea + act_runner**（裁定 U11）。**GitHub Actions 出局**——

github.com 在本机与工具链均实测不可达。



| 项 | 内容 |

|---|---|

| 触发 | push 到 main / develop / release/* / feature/* / hotfix/*；PR 到 main / develop |

| 运行环境 | Python 3.12 |

| 服务 | pgvector:pg16（5435）+ redis:7-alpine（6382）—— **只跑 test 环境** |

| 步骤 | 生成 CI 用 test 配置 → 装依赖 → 契约与单元测试 → **全场景用例库覆盖校验** → **评测数据导出** → 上传产物 |

### 14.3 增量事实的处理链路



```text

多源增量事实（对话 / 行为 / 设备 / 消费）

   ↓  写入强制携带 user_id（缺失即拒绝）

1. 置信度打分 —— 融合 Agent-Wiki 证据权重

   ↓

2. 三条数据治理规则

   ├─ 高分（≥0.82）→ 入库

   ├─ 低分        → 只留日志

   └─ 冲突标记    → 冲突人工复核队列（不进知识库）

   ↓  仅入库分支

3. 同步私有 Vault：Evidence 证据页 + Entity 实体页 + Claim 声明页（绑定证据 ID）

   ↓

4. 写变更审计（含 Wiki 页面变更历史）

```



**置信度融合公式**（实现参数，已显式登记）：



```text

evidence_score = Σ(reliabilityᵢ × weightᵢ) / Σ(weightᵢ)

coverage       = min(1, Σweightᵢ / 3.0)

influence      = 0.75 × coverage

confidence     = base × (1 − influence) + evidence_score × influence

```



两条**方向相反的不变量**由测试锁定：



- 中等基础分（0.5）+ 高可信证据 **必须**能跨过入库阈值 0.82 —— 否则「融合证据权重」是空话；

- 弱基础分（0.2）即使配满证据也 **不得**跨过阈值 —— 证据不能凭空造出结论。



**阈值不新造**：入库阈值沿用计划书【八】已有的 `jev_confidence_threshold = 0.82`。

## 16. P3 场景调度 Agent｜全流程总控

### 16.1 五层路由（冻结）



| 层 | 标识 | 实现 | 放弃条件 |

### 16.2 JEV-003：多意图冲突必须向用户确认



这是 P0-2 阶段唯一挂账的用例，本阶段落地。不变量有两条：



1. **澄清结论一旦成立，任何更低层都不得被调用** —— 测试用一个「若被调用就记录」的层证明它从未被触达；

2. **澄清不受置信阈值门控** —— 否则低置信时会漏掉必须的确认。



### 16.3 一处文档效力冲突（裁定 U25）



| 来源 | 主张 |

|---|---|

| 计划书（一、项目概述 + 三、P3）与 Skill-01 | Jev **不输出自由文本** |

| 早前裁定 U14（借鉴 CLAMBER） | 模型需输出 `clarifying_question` |



按效力顺序（计划书 ＞ Skills ＞ 架构文档 ＞ 台账）**计划书胜出**：

模型只输出 `require_clarification(0/1)` + `clarification_category`(枚举) + `candidate_labels`(枚举列表)，

**澄清话术由路由层按枚举键模板渲染**。这样既保留 U14 的结构化「必须澄清」契约，

又不违反禁自由文本。U14 其余部分继续有效。



### 16.4 LangGraph 主状态机



```text

START → route ─┬─(必须澄清)─→ clarify  ──→ END

               ├─(已定意图)─→ dispatch → aggregate → END

               └─(无法识别)─→ terminate → END

```



**踩到并修正的一个坑**：最初用 `StateGraph(dict)`，结果节点返回的部分更新会**整体替换** state，

route 的结果根本传不到 dispatch（表现为意图恒为 None、调用链恒为空）。

必须用 TypedDict schema，LangGraph 才会按键建立通道并做按键合并。

调度层的管道字段放在 `SchedulerState` 里，不污染 `agents.state` 的全局契约。



**权责强制**：调度器是唯一分发者；子 Agent 若试图改写

`user_id / session_id / login_status / jev_decision_result / wiki_digest`，

该次写入被拒绝并计入回滚（子 Agent 基类放行，由调度层拦截 —— 纵深防御）。



### 16.5 会话上下文管理与可观测

| 摘要压缩 | 抽取式摘要（不编造内容），压缩掉的轮次由摘要代表 |

| Trace ID 贯穿 | 存于 ContextVar，中间件/路由/状态机/子 Agent 自动拿到同一个 ID |

## 21. P6 内容质检 Agent｜全局防错、防幻、防假



### 21.1 隐私校验怎么做到「既不漏检、又不越界」



计划书三、P6 里有两条**必须一起读**的要求：



| 出处 | 要求 |

|---|---|

| 表注 | 「检测输出是否**混入其他用户隐私**；一旦发现**直接拦截输出并告警**」 |

| 步骤 6 | 「人工后台只能按 user_id 查看对应账号业务，**禁止批量遍历全部用户隐私**」 |



把别人的数据捞出来比对 = 违反第二条；不比对 = 违反第一条。

唯一自洽的解法是**基于引用来源的作用域校验**：



1. **引用作用域校验**：输出引用的每个 Claim/Evidence ID 都必须能在

   「本人私有 Vault 或公共 Workspace」内解析到。

2. **来源表（可选）**：生产者若提供「引用 ID → 归属账号」，可直接判出「越界引用他人数据」。

3. **显式标记扫描**：正文出现**他人账号标识**（自己的除外）→ 拦截并告警，兜底抓「手滑把 id 拼进文案」。



**一个必须讲清楚的现实**：行级隔离使得「读他人页面」与「页面不存在」**都返回 None**，

二者在读取侧不可区分。因此**越界引用在本系统里的可观测形态就是「解析不到」**，

所以 dangling 与 cross-user 同属拦截级 —— 这不是宽松，而是隔离之下的必然。



有一条用例用「一旦调用 list_* 就失败」的探针把实现方式钉死：

**隐私校验只能按引用逐条 read_page，不得遍历任何用户的数据。**



### 21.2 三层结论



| 结论 | 触发条件 | 处理 |

|---|---|---|

| **block** | 任何隐私问题 | 拦截输出 + 告警 + 入人工审核队列 |

| **downgrade** | 冲突 / 疑似幻觉 / 缺证据 | 降级提示风险 + 生成 `question.*` 待核实页 |

| **pass** | 无上述问题 | 放行 |



冲突是**内容问题**不是隐私事故，所以降级而不拦截。



### 21.3 四类冲突检测



| 类别 | 判据 |

|---|---|

| 时间 | 同一 `subject_id` 出现多个时间取值。**必须支持中文写法** —— 「六点半」「七点」只认阿拉伯数字会整类漏检（实现中曾漏，已修） |

| 费用 | 同一主体出现多个金额 |

| 空间 | 带空间语义（位于/出发/到达…）的命题中，同一主体指向不同客体 |

### 22.2 分层：纯 Dart 核心 + Flutter 外壳

## 24. P9 指标评估与增量微调体系｜持续优化体系

### 24.1 这一阶段是**先补台账再动手**的

P9 在原文里是一条裁定都没有的阶段。而「周期性增量微调」「SFT 数据集」「监控看板」
都没有定义实现方式——按项目约束，**未定义项一律登记台账并按开源借鉴处理**。
因此本轮先补齐四条：

| 裁定 | 内容 | 取证 |
|---|---|---|
| **U28** | 微调编排用 LLaMA-Factory；参数高效用 **LoRA**，显存不足退 4bit **QLoRA**；底层 PEFT | PyPI `llamafactory` / `peft`、官方 readthedocs |
| **U29** | 数据集用 LLaMA-Factory 的 **Alpaca** 格式（`instruction/input/output/system/history`） | 官方 readthedocs《数据处理》 |
| **U30** | 脱敏以 **Presidio** 为主 + 中文补充 + **自研正则确定性兜底** | PyPI `presidio-analyzer` / `presidio-anonymizer` |
| **U31** | 指标**由本项目计算并暴露**，Metabase 只是消费者 | metabase.com / grafana.com |

**一个必须记下的取证事实**：`github.com` 与 `raw.githubusercontent.com` 在本机
**实测不可达**（ConnectTimeout），与 U11 此前的结论一致。因此取证改用 PyPI 与官方文档站，
GitHub 地址只作上游 canonical 记录——**没有把「没验证到的东西」写成「已验证」**。

### 24.2 三个被实际运行抓出来的缺陷

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | 「证据缺失占比」写成 `getattr(page, "evidence_ids")`，而证据 id 存在 `extra` 里 | 该指标**恒为 100%**，看板会一直报假警 |
| 2 | 矛盾读数只认顶层 `contradicts`，但 `new_page` 会把未知关键字收进 extra | 内存构造的页面检不出矛盾（已改为顶层优先、extra 回落） |
| 3 | 模型层写成 `try: import presidio_analyzer` | 凭空引入一个**并未安装**的依赖，被依赖声明测试抓出 |

第 1 条尤其典型：**它不会报错，只会一直给出错误数字**。指标类代码的失败模式就是这样——
不跑测试根本发现不了。第 3 条改为**端口注入**（`Redactor(analyzer=...)`），
没注入就如实报告 `model_layer_active = False`，不冒充做了模型级脱敏。

### 24.3 隐私边界：三处「拒绝」而不是「过滤」

| 位置 | 规则 |
|---|---|
| 日志与看板出口 | `Redactor` **fail-closed**：无法证明已脱敏就抛错，不放行 |
| SFT 数据集 | 来源**白名单**：私有 Vault 直接**拒绝**，未列入的来源也拒绝（不是默认允许） |
| 样本本身 | 携带 `user_id` 直接拒绝——身份应在入口剥离，而不是留到后面再脱敏 |

### 24.4 一个必要的范围取舍：系统级看板只统计**公共 Workspace**

把私有 Vault 的内容聚合进全局看板，即使字段脱敏了，**小样本聚合本身就可能反推个体**。
因此看板默认 `scope="public"` 并把范围显式写进产出；要统计某账号就走私有视图。

### 24.5 范围声明：训练不进 CI

本机是 CPU 推理环境、无 GPU（U28）。因此 P9 交付的是**流水线编排与配置生成**：
该不该跑、跑哪个目标、用什么配置。`FinetunePipeline.as_dict()["training_in_ci"]` 恒为
`False`，并有断言守住——**不让 CI 假装跑过训练**。
样本不足时明确不跑（`200` 条为实现参数），因为用很少的数据反复微调只会把模型带偏。

## 25. P10 Harness 自进化闭环｜最后一个阶段

### 25.1 表 10 的措辞分两类，处置方式**不同**

这是本阶段最容易做错的地方。表 10 原文是：

> **禁止**移除 user_id 行级过滤与鉴权；**禁止**读取未脱敏私有 Vault；
> 修改 Jev 模板、Wiki 公共知识库大规模变更**强制人工审批**。

我第一版把四条全部按「禁止」处理（一律 deny）。它更严，但**把「迭代 Jev 模板」
这条计划书明确规定的流程整个堵死了**。比计划书更严并不等于更对。

现在拆成两组，并有断言守住：

| 组 | 红线 | 处置 |
|---|---|---|
| **禁止类** | 移除行级过滤/鉴权、读未脱敏私有 Vault | **deny**，不进审批 |
| **强制审批类** | 修改 Jev 模板、公共知识库大规模变更 | **needs_approval** |

红线扫描看的是 **diff 的删除行**：**新增**保护不算风险，**删掉**才算。

### 25.2 抓到的一个「虚假成功」

Agentic Loop 在决策层提案用尽时，我的兜底提案写的是 `done=True` ——
于是循环**在什么都没做的情况下报告「已达标，循环收敛」**。

这类 bug 不会让测试变红，它只让系统**在失败时报成功**。已改为 `done=False`，
由无进展规则收尾并如实标注「转人工」。同样的问题在测试辅助函数里也有一份，一并修了。

另外 `LoopResult.blocked` 曾在真正被拦截时恒为 `False`（DENY 分支直接 return，
没记下判定），已补 `verdict` 字段。

### 25.3 有界循环（裁定 U32）

离线链路会**自动改代码**。一个没有硬上限的自纠错循环，出错时的代价是持续改坏仓库，
而不是「多跑一会儿」。因此 `max_iterations = 8`、连续 2 轮无进展提前终止、
达上限归档为「未收敛」转人工 —— 都是**硬停**，不是建议。

### 25.4 三重闸门

| 闸门 | 位置 | 失败时 |
|---|---|---|
| Hook 链 | 变更进入沙箱**之前** | 任一 deny 即中止；**Hook 自身异常也 deny**（fail-closed） |
| 质检联动 | Hook 链内的 qa_link | 质检 block 则拒绝；**没有质检结论也需审批**，不默认放行 |
| 沙箱 | 执行时 | 命令白名单，未列入即拒绝 |

沙箱**控制的是「谁来执行」，不是「假定安全」** —— 所以它不是 Hook 的替代品（裁定 U34）。

### 25.5 离线隔离是结构性保证，不是承诺

`p10_harness` 的输出里带一段 `offline_isolation`，并有断言：

| 字段 | 值 |
|---|---|
| `touches_business_db` | False |
| `touches_private_vault` | False |

Agent-Wiki 维护 Skill 在**注册层**就只允许公共作用域，且「公共作用域却带 user_id」
会被单独拦下 —— 不指望调用方自觉。

## 26. 第二阶段｜旅游模块专项开发（第一个垂类样板）

### 26.1 表 12 的回退规则是**非对称**的，这一点最容易做错

表 12 原文：

> **仅任务完全超出业务域才允许回退**；本职范围内**参数缺失、数据采集失败、
> 方案生成失败禁止回退**，自行提示用户、重试或引导补充信息。

所以「允许回退」是**白名单**（只有一类），不是「按严重程度判断」：

| 失败类别 | 可否回退 | 处置 |
|---|---|---|
| `out_of_scope` | **可以** | 原路返回路由中枢 |
| `missing_parameter` | 禁止 | 询问用户补齐 |
| `collect_failed` | 禁止 | 重试 |
| `plan_failed` | 禁止 | 降级提示 |

代码里写成 `ROLLBACK_ALLOWED = frozenset({FAILURE_OUT_OF_SCOPE})` ——
**写成集合是为了让「多一类」在评审时变得显眼**。达到全局 2 次上限后，
即使超域也不再回退，避免与路由中枢形成甩锅循环。

还有一个容易含糊的点：**未在职责边界里声明的任务类别必须显式失败**，
不能默认按超域处理 —— 猜错就是把本职任务退回去甩锅，正是表 11 要防的事。

### 26.2 模块边界靠**结构**保证，不靠自觉

表 11 规定垂类「无权修改路由规则、无权分发任务给其他 Agent；跨模块请求必须通过
管家路由中枢中转；所有回退必须原路返回」。落地方式：

| 约束 | 实现 |
|---|---|
| 无路由权、无同级分发权 | `VerticalAgent.may_route = False`、`may_dispatch_to_peers = False` |
| 跨模块只能经管家 | `out_of_scope_request()` **只产描述、不执行**，且强制带 `relay_via: butler_agent` |
| 支付无权执行 | 只产出待付费清单，`executed=False` + `requires_manual_confirmation=True` |

### 26.3 重规划：**条件不成立就不该召大模型**

表 11 写的是「Jev 做条件判定…**条件成立才调用大模型重算路线**」。
如果每次都召模型问一遍「要不要重规划」，这句话就白写了。因此先做**确定性前置判定**：

| 触发 | 条件 |
|---|---|
| 景区临时闭园 | **必然**触发 |
| 天气变化 | 严重度 ≥ 阈值 |
| 交通延误 | 延误 **> 行程余量**（来得及就不重规划） |

三者都不成立时 `needs_llm=False`，**根本不进入模型调用**。

### 26.4 垂类脚手架（裁定 U39）

原文要求「点餐、售后直接**复制本模块结构**，替换业务逻辑、工具集即可」。
据此抽出 `VerticalAgent`，把**共有且不可省略**的四件事固化：

| # | 固化项 |
|---|---|
| 1 | 职责边界（✅必做 / ❌必回退） |
| 2 | 回退规则（仅超域可退，域内禁止） |
| 3 | 参数解析与缺失询问 |
| 4 | 结果归档到私有 Vault |

各垂类只填业务逻辑与工具集。旅游 Agent 是**第一个样板**。

## 28. P7 端侧语音引擎验证（真机之前的最后一层证据）

### 28.1 分层结论

P7 的适配器要跑在手机上，本机没有 Android 设备。但**引擎能否装上、模型是否完整、
唤醒词能否真的被检出**可以在本机验证。验证脚本
（`scripts/verify_voice_engine.py`）给**三层结论**，互不代替：

| 层 | 内容 | 本机结论 |
|---|---|---|
| **引擎层** | 引擎类可用、模型文件完整、唤醒词 token 合法 | ✅ **4/4 PASS** |
| **推理层** | 真实音频能否触发检出 | ✅ **PASS** |
| **真机层** | 麦克风权限、后台保活、功耗、Android 14 前台服务限制（U23） | 脚本**不假装覆盖** |

推理层实测：ASR 转写 0.wav 成功（66 字符）；用转写结果构造的 4 条关键词
（介绍 / 感兴趣 / 我想说的是 / 大家）**全部被 KWS 检出**。

### 28.2 差点被误判成「引擎不兼容」的一个数据缺陷

初次验证时**任何阈值都不触发检出**（阈值 0.05/0.10/0.25 × score 1.0/2.0/3.0 全组合），
看上去像模型与引擎版本代差。实际根因是：

> 模型仓里的 `test_wavs/test_keywords.txt` **与同目录的音频并不对应**。

用同一套模型当普通 ASR 转写 0.wav，得到的是
「对我做了介绍么我想说的是大家如果对我点酒感兴趣」——
里面**根本没有** test_keywords.txt 列的那些词（文森特卡索、周望军…）。

**正确做法**：先用 ASR 转写音频，再从转写结果里取**确实存在**的短语构造关键词。
这条经验已记入 MEMORY.md E-10 —— 否则下一个人还会再走一遍。

### 28.3 关键词 token 规则

每个音节要拆成「**声母 + 韵母**」两个 token：

| 词 | 拼音 token |
|---|---|
| 介绍 | `j` + `iè` + `sh` + `ào` |
| 感兴趣 | `g` + `ǎn` + `x` + `ìng` + `q` + `ù` |
| 你好管家 | `n` + `ǐ` + `h` + `ǎo` + `g` + `u` + `ǎn` + `j` + `i` + `ā` |

写成整音节（如 `shì`）引擎会打印 `Cannot find ID for token`。
「你好管家」的 10 个 token **全部在 tokens.txt 内**，脚本逐条校验。

## 29. Flutter 工具链打通 · Dart 侧语音绑定（P7 客户端链路）

### 29.1 Flutter 一直跑不起来的**真正原因**

此前多轮都把 flutter 的失败归因于「缺 git」「写不了 %APPDATA%」「pub 缓存在工作区外」，
逐个改都没解决，中途还累积了 **327 个 41.5MB 的快照副本（13.26 GB）**。

真相是：

> flutter 用**管道捕获** git log 的输出，而**沙箱禁止程序开管道捕获子进程输出**。

三条证据锁定它：

| 证据 | 说明 |
|---|---|
| git 其实装了 | git version 2.55.0.windows.3，在 C:\Program Files\Git |
| flutter SDK 有 .git | 不缺版本信息 |
| **同一条 git 命令单独跑完全成功** | 返回 commit hash，exit 0 —— 差别只在「有没有被管道捕获」 |

**解法**：对 flutter 命令使用一次性提权。随后一次通过：

```text
Flutter 3.47.7 • channel stable • Tools • Dart 3.13.5 • DevTools 2.60.0
```

同一个原因此前也让 dart test 失败过（见 E-08/E-09）。
**以后遇到「子进程相关」的沙箱拒绝，先想到管道这一条。**

### 29.2 打通之后做到了什么

| 步骤 | 结果 |
|---|---|
| flutter pub get | 66 个依赖解析成功，含 sherpa_onnx 1.13.8 |
| Windows 原生库 | sherpa_onnx_windows 包带 sherpa-onnx-c-api.dll（4.4MB）与 onnxruntime.dll（17MB） |
| 新建 aibutler_voice 包 | 引擎绑定独立成包：**core 放业务规则（零原生依赖），voice 放引擎绑定** |
| Dart 侧引擎代码 | WakeWordEngine 按官方 Dart API 写（KeywordSpotter / createStream / acceptWaveform / decode / getResult / reset） |

Dart 侧验证实测通过 3 项：**绑定初始化**、**「你好管家」10 个 token 全部合法**、
**读取音频（89784 采样 @16000Hz）**。

### 29.3 真正的根因：**System32 里躺着一个上古 onnxruntime.dll**

Dart 侧加载模型时报
`The given version [28] is not supported, only version 1 to 10 is supported in this build`，
随后**访问冲突崩溃**。报错里的「1 to 10」不是巧合：

> `C:\Windows\System32\onnxruntime.dll` 是 Windows 自带的 **1.10.220126**（Windows ML 用的）。

Windows 解析 DLL 依赖的顺序是「**exe 目录 → System32 → PATH**」——
**DLL 自己所在目录并不优先**。于是 sherpa-onnx 拿到的 ORT API 是 10，而它需要 28。

**证据链**（每一步都是实测）：

| # | 实验 | 结果 |
|---|---|---|
| 1 | 列出 System32 的 onnxruntime | `1.10.220126` —— 与报错里的「1 to 10」吻合 |
| 2 | 用 **ctypes** 直接调同一个 `sherpa-onnx-c-api.dll`（`os.add_dll_directory` 指对目录） | **创建引擎成功** —— 库与结构体都没问题 |
| 3 | Dart 把正确目录加进 PATH | 仍然崩 —— **System32 优先于 PATH** |
| 4 | 改成先按**绝对路径** `DynamicLibrary.open(onnxruntime.dll)` 预加载 | **一次通过**；此时 PATH 里故意不放 dll 目录 |

**解法**（已落在 `aibutler_voice` 的 `preloadNativeLibraries`）：

```dart
DynamicLibrary.open(dllDir + sep + 'onnxruntime.dll');        // 先依赖
DynamicLibrary.open(dllDir + sep + 'sherpa-onnx-c-api.dll');  // 后被依赖者
sherpa.initBindings();
```

**顺序不能反。** 已加载模块按基名复用，后续依赖解析不再去 System32 找。

### 29.3.1 一次错误诊断的更正

排查中途我曾判断「pub 的 `package:sherpa_onnx` Dart 绑定 FFI 结构体与 C 库字段顺序不一致」，
并写进了 MEMORY E-12。**该结论是错的**：按上面的预加载修复后，
**pub 的包构建完全正常**，我手写的绑定与它都能跑通。

错在哪：看到「配置打印正确但模型加载崩」，我直接归因给了绑定库，
**没有先怀疑 DLL 解析**。E-12 已标作废，真实根因记在 **E-13**。

另外**两个无效实验**也值得记下来：

- 用「字符串搜索 DLL 里有没有 `wenet_ctc`」当作结构体布局证据 —— 搜到的是**字符串值**，不是字段名，**该实验证明不了任何布局问题**；
- 「先取局部变量再写嵌套结构体字段」被我当成越界原因 —— 实测局部变量**也是视图**，写入正常。

真正起作用的是 **ctypes 那次实验**：它把「库的问题」与「调用方的问题」**干净地一分为二**。
**能把问题一分为二的实验，比任何推理都值钱。**

### 29.3.2 同类风险提示

任何依赖 `onnxruntime.dll` 的原生库在 Windows 上都可能踩这个坑。
本机 `System32` 之外还有 Edge / Office / WSL 带的一堆 onnxruntime（1.19 / 1.23 / 1.24 / 1.29），

## 30. 环境自愈：临时目录与原生库加载

### 30.1 系统临时目录不可写会让 chromadb 整片报错

某些沙箱模式下 `C:\Users\<用户>\AppData\Local\Temp` **不可写**。
Python 于是**静默降级**把临时目录落到当前目录，而 chromadb 的 rust 绑定要自己在临时目录建库 ——
建不了就报 `unable to open database file`，**与业务代码毫无关系**，
却会让一整片 RAG 用例集体 ERROR。

**一个把我带偏的细节**：`tempfile.gettempdir()` 在该目录不可用时**会返回当前目录**，
所以「探一下 gettempdir() 能不能写」这种自愈逻辑**必然通过、等于没探**。
正确做法是直接探**环境变量指向的路径**。

解法落在 `tests/conftest.py` 的 `_ensure_writable_temp`：导入被测模块之前先探，
不可写就把 `TMP` / `TEMP` / `TMPDIR` 指到工作区内的 `.pytest_tmp`。
**pytest 在任何沙箱模式下都能跑。**

> 排查顺序上的教训：看到「一整片用例连同报数据库错误」，
> **先怀疑环境（临时目录、文件句柄），再怀疑代码。**

### 30.2 Windows 原生库必须先按绝对路径预加载

见 29.3。这条不只影响语音：**任何依赖 `onnxruntime.dll` 的原生库在 Windows 上都可能踩坑**。
通用做法是「先按绝对路径 load 依赖，再 load 被依赖者」。

### 30.3 用例库新增 `dart-script:` 引用形式

Dart 侧既有 **测试**（`test('用例名', ...)`）也有 **验证脚本**（`main()` 形式，
如 `verify_kws.dart`）。用例库现在支持三种引用：

| 形式 | 含义 |
|---|---|
| `tests/xxx.py::test_name` | Python 用例 |
| `dart:.../xxx_test.dart::用例名` | Dart 测试 |
| `dart-script:.../xxx.dart` | Dart 验证脚本（校验存在 `void main(`） |

### 32.2 编译/测试暴露并修掉的三个真问题

都不是「为了让测试变绿」而改的，是**代码本身的缺陷**：

1. **会话失效弹窗在首次构建时不触发**（三、P7 步骤5）
   弹窗只写在 `didUpdateWidget` 里，于是「App 启动时就发现会话已失效」这条路径下，
   用户看到的是一个沉默的对话页，而不是重新登录引导。已抽出
   `_maybeShowExpiredDialog`，`initState` 与 `didUpdateWidget` 都调用。

2. **唤醒适配器缺必填参数导致编译失败**
   `SherpaWakeWord` 要求 `model`，而 `main.dart` 没传。
   按与其他适配器**同一条政策**改为可空 + `start()` 时明确报错并指向裁定 U06，
   **不做静默的假实现**。

3. **`main.dart` 根本没有 `dispose()`**
   唤醒引擎与语音流水线**从未被释放**。二者都持有原生资源（sherpa-onnx 会话），
   不释放就是实打实的泄漏。已补 `State.dispose` 并给 `VoicePipeline` 加了
   `dispose()`（逐个端口 `try/catch` 停，避免某个没启动过拖累其余释放）。

> **一个方法上的教训**：我用脚本改文件时**无条件打印了「已修改」**，
> 结果锚点没命中、写回了原内容，我却以为改好了 —— 白跑了两轮构建。
> 后来改用会在锚点不匹配时**直接报错**的工具，问题立刻现形。
> **「我以为改了」和「确认改了」之间的差距，就是两轮构建的时间。**

### 32.3 APK 构建还差什么（如实记录）　→ **已解决，见第 33 节；本节对成因的判断是错的**

app-armeabi-v7a-release.apk    32.1 MB
app-x86_64-release.apk         47.6 MB

### 33.2 第 32.3 节把它记成了「AGP 的 bug」，那个判断是错的

第 32.3 节写着卡在 `MalformedJsonException: Invalid escape sequence ... $.cleanCommandsComponents`，
并推测是「AGP 解析 CMake 模型的 Gson 转义报错」。**把它当成第三方工具的缺陷是错的。**

真相是 **AGP 生成的 `android_gradle_build.json` 本身就是非法 JSON** ——
里面的 ninja 路径写着被毁坏的中文用户名（替换字符），产生了非法转义序列。

证据在 `build/jni/intermediates/cxx/.../logs/<abi>/metadata_generation_record.json`，
它把原因直接写了出来："JSON generation completed with problem. Exception: ..." ——
**只要去看这个文件，就不必猜。**

### 33.3 三步修复（缺一不可）

| # | 做法 | 为什么必须 |
|---|---|---|
| 1 | 把 Android SDK 放到**真正的 ASCII 目录** `D:/android-sdk` | **目录联接不够** —— AGP 会把联接解析回带中文的真实路径 |
| 2 | `flutter config --android-sdk D:/android-sdk` | 它决定 Flutter 往 `local.properties` 里写什么 |
| 3 | 删 `local.properties` 让其重写；构建前清 `build/` 与 pub 缓存的 `.cxx` | 旧值/旧中间产物会一直沿用 |

### 33.4 与第 32.3 节推测的另一半对照

第 32.3 节还推测「:`jni` 需要 NDK」。NDK 与 CMake 确实装上了，
但**装完之后错误一字不差** —— 说明它们当时并不是阻塞点。
链条是 `flutter_secure_storage` → `flutter_secure_storage_windows` → `path_provider` → `path_provider_android` → `jni`。

> **教训**：报错信息里出现别人的类名（这里是一条 Gson 异常），
> 很容易让人判定「这是别人的 bug」。

## 34. P7 真机准备：权限、前台服务与真实录音

### 34.1 一个必须先说清楚的事实

第 33 节把 APK 构建打通了，但用 `aapt2 dump badging` 一看清单，**只有一条权限**：

```text
uses-permission: name=android.permission.INTERNET
```

也就是说：**那个 APK 装到手机上，语音功能一点都用不了**（没有 RECORD_AUDIO），
而 `RecorderMicrophone.start()` 当时是直接抛「需要录音插件」的。
「能构建出 APK」与「能在真机上跑」之间，差的就是这一节。

另外 `targetSdk = 36`（Android 16），意味着 **Android 14+ 的规则全部适用**：
前台服务必须声明类型并持有对应权限，否则 `startForeground` 直接抛异常。
这正是裁定 U23 所指的那一层。

### 34.2 补齐的三件事

| # | 内容 | 依据 |
|---|---|---|
| 1 | **清单权限 9 条**（RECORD_AUDIO / FOREGROUND_SERVICE / FOREGROUND_SERVICE_MICROPHONE / POST_NOTIFICATIONS / WAKE_LOCK / 定位 / 音频设置 / 网络） | 三、P7；U23 |
| 2 | **前台服务** `WakeWordForegroundService`（`foregroundServiceType="microphone"`）+ MethodChannel | 三、P7「离线唤醒、随时打断」；U23 |
| 3 | **真实录音** `RecorderMicrophone`（record 7.1.2，16kHz 单声道 PCM16 转浮点） | 三、P7「双输入」 |

第 1 条为什么必须是前台服务而不是普通后台任务：

> Android 8+ 限制后台应用访问麦克风；Android 14+ 还要求前台服务
> **声明类型并持有对应权限**，否则启动即抛 `SecurityException`。
> 「揣在兜里也能喊醒」在 Android 14+ 上**只能靠它成立**。

录音的采样格式是**跟着唤醒词模型定的**（U06 的 wenetspeech ZipFormer 要 16kHz），
不是随手选的 —— 采样率不对，唤醒词引擎拿到的就是错的东西。
PCM16 转浮点时按两字节一采样切，落单的半个采样**留到下一块**，否则波形会整体错位。

### 34.3 把「声明层」纳入机检

`scripts/verify_android_artifact.py` 已扩展：除原有的原生库检查外，
再用 `aapt2` 读 APK 清单，核对 **9 条权限**与 **foregroundServiceType=microphone**。

脚本自己把话说清楚，避免把「声明齐了」读成「真机跑通了」：

| 层次 | 覆盖 | 谁能回答 |
|---|---|---|
| **声明层** | 原生库是否随包、权限是否声明、服务类型是否正确 | 本脚本 |
| **运行时层** | 用户是否真的授权、前台服务能否长期存活、实际功耗、兜里能否唤醒 | **只有真机**（U23） |

### 34.4 模拟器这条路走不通（已实测）

本想用 Android 模拟器替代真机来回答一部分问题，实测两条硬门槛都过不去：

| 门槛 | 实测 |
|---|---|
| 硬件加速 | 已有 hypervisor 在跑（`HypervisorPresent: True`），但 **WHPX 功能未启用**，启用需重启 |
| 内存 | 可用仅 **2.25 GB**，模拟器本身要 2–4 GB |

所以这一节做的是**把真机验证的前置条件备齐**，而不是替代真机验证。

### 34.5 一个 XML 小坑

第一次重建时清单解析失败：`ManifestMerger2$MergeFailureException: Error parsing AndroidManifest.xml`。
原因是我在 XML 注释里画了分隔线 —— **XML 注释中不允许出现连续两个连字符**。
改掉后清单解析通过（9 条权限 + 1 个服务）。

## 35. P7 端侧能力闭环：唤醒词随包、常驻服务、真实录音

### 35.1 上一轮留下的空洞

第 34 节把权限与服务声明补齐了，但**能力本身还是空的**：

| 空洞 | 后果 |
|---|---|
| 唤醒词模型**没有随包** | `SherpaWakeWord` 拿不到模型，装上去也唤不醒 |
| 前台服务的桥建好了却**没接进流程** | 服务永远不会被拉起，「后台常驻」只停在声明上 |

### 35.2 唤醒词随包（裁定 U06）

模型共 **4.82 MB**（encoder 4.58 / decoder 0.17 / joiner 0.06 / tokens），随包下发。
理由写进 pubspec 注释了：**U06 要的是离线唤醒** —— 若靠首次启动下载，第一次断网就唤不醒，
「离线」二字不成立。

assets 在 APK 里是压缩资源，**不能直接当路径**给 sherpa-onnx，
所以新增 `lib/adapters/asset_models.dart`：首次启动释放到应用私有目录，
之后按「文件存在且大小一致」跳过，不重复写那 4.8 MB。

解析是异步的，而引擎在 build 期间构造 —— 所以给 `SherpaWakeWord` 加了
`modelResolver`：**等真正 start() 时再解析路径**。

### 35.3 一个必须拦下来的问题：模型仓自带的唤醒词含第三方商标

模型仓的 `keywords.txt` 里是 `你好军哥 / 蛋哥蛋哥 / 小爱同学 / 你好问问 / 小艺小艺 / 小米小米` ——
**其中三条是别家产品的唤醒词与商标**。直接随包下发是不合适的。

本项目的唤醒词取自**裁定 U06**（不是自己定的）：

```text
 n ǐ h ǎo g u ǎn j i ā @你好管家
```

现在 `verify_android_artifact.py` 会**从 APK 里把那几个词搜一遍**，
出现即判失败。这条检查防的不是「写错」，而是「有人顺手把模型仓那份拷进来」。

### 35.4 常驻唤醒前台服务接进流程

| 时机 | 动作 | 理由 |
|---|---|---|
| 登录成功 / 会话恢复 | `_wakeService.start()` | 唤醒后要先校验会话，未登录时后台常驻只是白耗电 |
| 登出 | `_wakeService.stop()` | 登出就别再占着麦克风常驻 |

而不是「App 用不了」。所以如实把原因作为一条消息显示出来，照常继续。

## 37. CI 流水线：一条会立刻失败的顺序错误，与它自己的守护

### 37.1 CI 里一个会让第一次运行就失败的 bug

`.github/workflows/ci.yml` 里，生成 `.env.test` 的那一步开头是：

```yaml
run: |
  python - <<PY
  from cryptography.fernet import Fernet     # 这里就要用到
  ...
  PY
  pip install cryptography                   # 却在之后才装
```

shell 是**顺序执行**的 —— `python` 先跑，那时候 `cryptography` 还没装。
而 `pip install -r requirements.txt` 整一步排在更后面。**CI 第一次运行就会 ImportError。**

修法是把「安装依赖」提到「生成 test 环境配置」之前，并在文件头写明这条硬要求。

### 37.2 CI 是最容易悄悄腐坏的东西

它平时不跑、没人看，而且**新加的验证脚本不会自动进 CI**。
本项目陆续加了 P0 冒烟、语音引擎验证、Dart 核心测试 —— 原来的 CI 一条都没覆盖。

本轮补齐后，流水线是两个 job：

| job | 覆盖 |
|---|---|
| `test`（Python 3.12 + PostgreSQL + Redis） | 单元测试 → **模拟 CI 依赖面**（`AIBUTLER_BLOCK_ML=1`）→ 用例库覆盖率 → **P0-1 冒烟** → P1–P4 冒烟 → **语音引擎验证** → 评测导出 |
| `dart-core`（Dart） | 依赖解析 → 静态分析 → 单元测试。纯 Dart、零原生依赖，普通 Linux runner 即可 |

### 37.3 给 CI 本身加守护 —— 以及第一版守护**是绿的**

新增 `tests/test_ci_pipeline.py`：校验 YAML 可解析、必需的验证入口都在、
点名的脚本真的存在、以及**装依赖必须排在用到依赖的步骤之前**。

写完当然是绿的。于是把顺序 bug **原样放回去**看它会不会红 —— 结果：

```text
.....  5 passed      ← 没抓住
```

原因：CI 里写的是 `from cryptography.fernet import Fernet`，
而我的判据只认 `import cryptography`。**守护在真正的 bug 面前是绿的。**

改成同时识别 `import X` 与 `from X import ...` 之后：

```text
E  AssertionError: 第 3 步「生成 CI 用 test 环境配置」用到了 cryptography，
   但它排在安装依赖（第 4 步）之前
```

> 这一步是**给守护本身做的验收**。
> 不故意造一次违规、看它红，就不知道它到底在不在工作 ——
> 而「守护是绿的」与「守护有效」是两件不同的事。

## 38. P0-2 能力面：把「声明」改成「实测」

### 38.1 digest 里写死的能力清单

`p0_devkit.py` 的 digest 原先是这样报能力的：

```python
"capabilities": ["scaffold", "testkit", "prompt_registry",
                 "scenario_library", "evaluation", "log_query"],
```

**写死的字符串** —— 它声称拥有这 6 项，但其中 `scaffold` / `prompt_registry` / `log_query`
从没被 import 过。**模块被改名或删掉，digest 依然报「有」。**

这正是第 35 节记下的那条教训 —— **声明 ≠ 能力** —— 只不过这次出在本项目自己的代码里。
同一个 digest 里，`scenario_categories` / `case_total` 都是真算出来的，唯独能力面是手抄的。

### 38.2 改成实测

新增 `_probe_capabilities()`：逐个 `importlib.import_module`，
返回（可用, 缺失）两个列表。digest 同时报出 `capabilities` 与 `capabilities_missing` ——
**只报好消息等于没报**。

### 38.3 守护，以及守护自己的验收

`tests/test_agents_p0_devkit.py` 有五条，其中一条是关键：

> `test_probe_really_detects_a_missing_module`：用 monkeypatch 往清单里塞一个
> 不存在的模块，断言它落进 `missing`。

没有这一条，另外几条都无法证明探测真的在工作 ——
**一个永远返回「全都在」的实现同样能让它们变绿。**
（第 37 节刚踩过同一个坑：CI 守护的第一版在真 bug 面前是绿的。）

### 38.4 一个据实记录的缺口：自动部署流水线

计划书三、P0-2 的原话包含「CI 自动构建、**自动部署流水线**」。当前状态：

| 项 | 状态 |
|---|---|
| CI 自动构建 | 已落地（`.github/workflows/ci.yml`，两个 job，见第 37 节） |
| 可部署产物 | 已落地（`deploy/Dockerfile` + `deploy/compose/`） |
| **自动部署流水线** | **未落地** |

原因不是遗漏，而是**部署目标已由台账裁定缓做**：

也就是说：**流水线的载体已选型、产物已具备，唯独目标环境尚未接入。**
在此之前写一条无法运行的部署流水线，属于无据构建 —— 故据实登记为缺口，
待 ECS 接入时一并补上。

## 39. 系统排查「写死而非推导」：又找到两处

### 39.1 排查方法

第 38 节在 P0-2 抓到一处写死的能力清单后，把范围扩到**所有阶段 Agent 的 digest**：
逐个看它们的返回值是「import 来的 / 算出来的」还是「手抄的」。

| Agent | digest 里的值 | 判定 |
|---|---|---|
| P0-1 | `list(ENV_NAMES)` / `list(ZONES)` / 从 settings 取 | 推导 ✓ |
| P1 | 真实 SDK 读数 | 实测 ✓ |
| P2 | 真实检索响应 | 实测 ✓ |
| P3 | `list(LAYERS)` / `MAX_ROLLBACKS` | 推导 ✓ |
| P4 | `len(ROSTER)` / `roster_manifest()` | 推导 ✓ |
| P10 | `ran: False` + 原因 | 如实 ✓ |
| **P0-2** | 能力清单 | **写死**（第 38 节已修） |
| **P9** | `regex_layer: True` | **写死**（本节修复） |

### 39.2 P9：`regex_layer` 是硬编码的 `True`

P9 的评估报告里报脱敏两层：

```python
"redaction": {"regex_layer": True,                    # ← 写死
               "model_layer": redactor.model_layer_active},
```

对比很刺眼：`model_layer` 是**端口注入推导**的（`analyzer is not None`，
注释里还专门写了为什么不用「try import」），而它旁边的 `regex_layer` 直接手写 True。
规则表被清空、额外规则配错，它照样报「已脱敏」。

修法：给 `Redactor` 补一个与 `model_layer_active` 对称的属性 ——

```python
@property
def regex_layer_active(self) -> bool:
    """正则层是否**真的**有规则在跑。不是恒 True。"""
    return bool(self._compiled)
```

P9 改为读这两个属性，**两层都从 redactor 推导**。

### 39.3 守护：让「写死」这件事本身可测

原有的 `test_agent_reports_redaction_layers` 只断言默认情况下是 `True` ——
**一个恒返回 True 的实现同样能过**。补两条：

1. 把 `_PATTERNS` 清空，`Redactor().regex_layer_active` 必须为 `False`；
2. 同样清空后，**Agent 报出来的**也必须是 `False`。

把写死的 `True` 放回去复验：

```text
E  AssertionError: Agent 的 digest 没有跟着 redactor 走 —— 说明那里是写死的
E  assert True is False
```

### 39.4 一条待观察的同类现象（暂不改）

P4 的 digest 里有一句手写的 `trigger` 描述（「全局状态变更自动触发…会话失效则跳过执行」）。
它**当前是准确的**（会话失效即跳过有测试覆盖），但同样属于「手抄的事实」。
与布尔标志不同的是，这句话**没有可推导的来源**，改成从代码生成反而会造出噪音，
故据实记录、暂不改动。

## 40. 死代码审计：找出两处「写好了却从没接上」

### 40.1 审计方法

不引入任何新依赖（项目没有 linter，也无据可依去加），用标准库 `ast` 扫：
顶层定义全项目出现次数为 0 的，就是候选。
113 个文件、504 个顶层定义 → **8 个零引用**。

### 40.2 一处是误报

`_enforce_user_scope_on_write`（`core/db.py`）看着零引用，其实是
`@event.listens_for(Session, "before_flush")` 注册的 —— **装饰器注册就是引用**，
SQLAlchemy 会自己调它。行级隔离的写入侧防护并未缺失。

### 40.3 第一处真问题：`mask_account` 写好了却没进规则表

`core/security.py` 里定义了四个掩码函数，但 `log_safety.py` 的 `MASK_RULES` 只用了三个：

```text
mask_phone       -> 已接入（phone / mobile / tel / 手机）
mask_bank_card   -> 已接入（bank / card / account_no）
mask_location    -> 已接入（location / address / geo / ...）
mask_account     -> **从未接入**
```

后果很直接：字段名叫 `account` 的日志**一点都没脱敏**，原样落盘。
而七、13 要求「全链路日志…全部做隐私脱敏」。

修法是补一条规则，**并注意顺序**：

```python
MASK_RULES = (
    (("phone", ...), mask_phone),
    (("bank", "card", "银行卡", "account_no"), mask_bank_card),   # 必须在前
    (("account", "账号", "账户"), mask_account),
    ...
)
```

`_field_masker` 返回**第一个**命中的规则，而 `"account_no"` 同时含有两个关键字。
账号规则若排到前面，银行卡号就会被按账号掩码处理，**掩码强度下降**。
所以补了两条测试：字段确被掩码 + 顺序不得调换。调换后复验：

```text
E  AssertionError: assert <function mask_account> is <function mask_bank_card>
   where <function mask_account> = _field_masker("account_no")
```

### 40.4 第二处真问题：`logout()` 既没被调用也没被测过

会话生命周期一共三个函数：

| 函数 | 调用 | 测试 |
|---|---|---|
| `login()` | 有 | 有 |
| `force_logout()` | 有 | 有 |
| **`logout()`** | **无** | **无** |

`logout()` 处理的是「**凭证主动作废**」—— 正是最不该未经验证的那类路径。
已补一条测试：单端登出后该 token 立刻 401（不必等 TTL），**且不牵连同账号其它设备**。

### 40.5 其余零引用定义（据实记录，暂不处理）

| 定义 | 位置 | 判断 |
|---|---|---|
| `MopsError` / `LoopError` | `agents/mops.py` / `harness/loop.py` | 异常类，当前无人 raise。可能是留给调用方 catch 的扩展点 |
| `get_settings()` | `core/config.py` | `lru_cache` 包装，当前无人调用 |
| `make_state_for()` | `devkit/testkit.py` | 夹具，同类 `make_state` 在用 |
| `LoggingObserver` | `scheduler/observe.py` | 埋点观察者实现，当前未接线 |

这些**不属于「写好了却漏接」**（不像 `mask_account` 那样有明确的该接之处），
删掉又可能是在删未来的扩展点，故据实登记、不擅自改动。

## 41. 核对「按验收清单来查」够不够：八要素里漏了一个

### 41.1 先查了两处，结论是「没问题」

审计不该只报问题，**查过而确认没问题的也要记下来**，否则下次还得重查一遍。

**其一：重复定义的常量会不会漂移。**
`MAX_ROLLBACKS = 2` 在 `scheduler/graph.py` 与 `verticals/base.py` **各定义了一份**。
看起来是漂移隐患，但两处**各有一条测试把它钉死在 2**：
`test_scheduler_graph.py::assert MAX_ROLLBACKS == 2` 与
`test_vertical_tour.py::assert MAX_ROLLBACKS == 2, "表 12 写的是全局 2 次上限"`。
任一处改动都会立刻变红 → **不是缺口**。

**其二：两个名字相近、值不同的限制是不是矛盾。**
`harness/loop.py::NO_PROGRESS_LIMIT = 2`（Agentic Loop，裁定 U32）与
`scheduler/tools.py::DEFAULT_NO_PROGRESS_LIMIT = 3`（工具调用层的「无增量」判定）
看着像同一个东西给了两个值。核对后确认：**层次不同**（循环轮次 vs 工具调用次数），
且项目有自己的登记约定 —— 计划书定义的参数进表 13、未定义决策进台账、
**局部可调参数用代码内联的「（实现参数）」标注**（全项目约 50 处，U32 已覆盖循环上限）。
两处都遵守了这个约定 → **不是缺口**。

### 41.2 真问题：只按验收清单查，会漏掉清单没点名的那一个

计划书对本体的定义是**八要素**（《Agent-Wiki 知识库开发规范》§1 逐字引用了原文）：
实体、来源、声明、证据、关系、矛盾、开放问题、综合摘要。
而验收标准七、18 只点了其中**六项**（没有实体与综合摘要）。

此前的测试是这么覆盖的：

| 测试 | 覆盖 |
|---|---|
| `test_ontology_has_all_six_elements_from_criterion_18` | 验收 18 的六项 |
| `test_ontology_also_covers_synthesis_for_criterion_20` | synthesis（验收 20） |
| **Entity** | **无人覆盖** |

两条合起来看着像齐了，实则少一个 —— **而少了不会报错**。
`ENTITY` 在别处被用到（置信度同步、P5 事实），但**从没对照计划书的本体要求检查过**：
它是否登记进 `PAGE_TYPES`、必填字段是否为 `(name, entity_type)`。

### 41.3 修法：按计划书原文查，而不是按验收清单查

补两条，并把完整清单显式写出来：

```python
PLAN_ONTOLOGY_ELEMENTS = ("ENTITY", "SOURCE", "CLAIM", "EVIDENCE",
                         "RELATION", "CONTRADICTION", "QUESTION", "SYNTHESIS")
```

| 新测试 | 作用 |
|---|---|
| `test_ontology_covers_every_element_the_plan_defines` | 八个都要在，且 `PAGE_TYPES` 数量相符 |
| `test_every_element_declares_required_fields_including_entity` | 必填字段覆盖**全部**八项 |

把 `ENTITY` 从 `PAGE_TYPES` 摘掉复验：

```text
E  AssertionError: ENTITY 未登记进 PAGE_TYPES
E  assert "entity" in ("source", "claim", "evidence", ...)
```

### 41.4 一条可复用的教训

> **验收清单是「最低门槛」，不是「全部要求」。**
> 验收 18 列了六项，那条测试就只查六项 —— 于是计划书里明明写着的第八项无人过问。
> 凡是「清单式」的检查，都要回头问一句：**这份清单本身是否穷尽了真值源？**

## 42. 把「18」和「12」拿回计划书原文核对了一次

### 42.1 起因：那两条测试其实自证不了

`test_acceptance.py` 里有：

```python
def test_table_13_has_every_plan_parameter():
    assert len(TABLE_13) == 18        # 「18」是我写死的
...
def test_reusable_asset_library_has_twelve_entries():
    assert len(REUSABLE_ASSETS) == 12 # 「12」也是我写死的
```

**这是循环验证**：数字来自我当初对计划书的转录，测试再拿它去校验同一份转录。
若当初抄漏了一个，这两条**照样绿**。

### 42.2 于是拿原文对了一遍

计划书【八】的表 13 原文：

| 分组 | 参数个数 |
|---|---|
| 五层路由&Agent生态全局硬参数 | 8 |
| Jev 决策模型配置 | 4 |
| Agent-Wiki v2 知识库配置 | 6 |
| **合计** | **18** |

逐项比对 `TABLE_13`：**18 个全部对上，分组 8/4/6 也一致**，数值逐个相符。

计划书【六】的资产清单逐条数：**也是 12 条**，与 `REUSABLE_ASSETS` 逐项对应。

**结论：两处登记都是准确的。** 但这份准确性**来自仓库之外的一次人工核对**，
不是仓库自己能证明的 —— 计划书原件不在仓库里（也不该放进来）。
这一点如实记下，免得后人误以为那两条测试提供了它们提供不了的保证。

### 42.3 核对时揪出一处「有意偏离计划书却没写理由」

逐条比对时，第 12 条对不上：

```text
计划书：基于 Claude Code 的全自动系统自进化闭环
代码  ：全自动系统自进化闭环          <- 少了「基于 Claude Code」
```

这不是抄漏。查台账：**裁定 U08**（人工授权）明令
「**不引入 Claude Code 本体**；仅借用其设计思维…自研 Agentic Loop」。
名称是照裁定改的，**改得对**。

问题在于：**代码里一个字都没说明**。该条资产的 `note` 是空的。
于是任何人都可能「照着计划书把它修正回去」—— 而那会与 U08 冲突，
**且改回去不会有任何测试变红**（资产名称此前没有任何约束）。

### 42.4 修法与守护

给第 12 条补上备注，并加一条测试把「名称」与「裁定」绑在一起：

```text
asset.note == "自研 Agentic Loop，非 Claude Code 本体（裁定 U08）"
```

测试同时断言三件事：名称里不含 Claude Code、备注里写明依据、
**以及 U08 的内容本身仍是「不引入 Claude Code 本体」** —— 依据被改，这条就失效。

把名称「修正」回计划书原文复验：

```text
E  AssertionError: 资产名称不应写 Claude Code —— 裁定 U08 明令不引入其本体
E  assert "Claude Code" not in "基于 Claude Code 的全自动系统自进化闭环"
```

### 42.5 一条可复用的做法

> 当代码与计划书**有意不一致**时，**不一致本身就是需要登记的事实**。
> 只写「照裁定改的」还不够 —— 要写清**是哪条裁定**，并让测试把它绑住；
> 否则后人看到差异，第一反应就是「修正」回去。

> 但 `load_settings(**overrides)` 是公开 API，不传 `_env_file=`，

> **运行时切换环境是做不到的**。文档里已如实写明，免得后人照着自己的直觉去用它。



### 48.3 第二件：真缺口 —— 文件里的值没人管



原有的四环境测试其实很扎实：



| 测试 | 验的是 |

|---|---|

| `test_environments_share_no_resource` | `assert_disjoint()` —— 校验**声明对象** |

| `test_every_environment_has_its_own_config_file` | 四个文件**存在** |

| `test_secrets_are_not_shared_between_environments` | 三个**密钥**字段互不相同 |

| `test_only_local_environments_expose_host_ports` | 暴露端口策略 |



**唯独没有校验：文件里的端口 / 库 / 存储根。**

于是把 `.env.prod` 的 `POSTGRES_PORT` 与 `POSTGRES_DB` 改成 dev 的 ——

**不会有任何测试变红**，而「四环境完全独立隔离」是一条计划书硬要求（三、P0-1）。

这类事故正是第 48.2 节那个运行时守卫想拦的，但守卫只在启动时跑，**配置写错却没人拦**。



### 48.4 补两条守护



| 测试 | 作用 |

|---|---|

| `test_env_files_match_their_environment_declaration` | 每个文件的 `ENVIRONMENT` / 端口 / 库 / 存储根 / Wiki 根都要与声明一致 |

| `test_env_files_share_no_resource_either` | 四个**文件**之间五个字段都不得重复 |



两条都在**读文件**，而不是读声明对象 —— 「声明对」与「文件对」是两件事。



把 `.env.prod` 改成 dev 的端口与库复验：



```text

E  AssertionError: POSTGRES_PORT 在四环境文件间出现重复：

   {dev: 5434, test: 5435, staging: 5436, prod: 5434}

```



### 48.5 一条可复用的教训



> **「配置正确」不能靠声明来证明，要读真正被加载的那份。**

> `assert_disjoint()` 校验的是代码里的声明对象；

> 而真正决定连哪个库的，是 `.env.*` 里的那几行字。

> 两者都要守，缺一不可。

## 49. 部署产物：变量引用缺一个，compose 会**静默**用空值



顺着第 48 节的思路往下推一层：**声明对了、文件对了，那真正被使用它们的那份呢？**



### 49.1 先确认设计本身是稳的



`deploy/compose/` 两个文件：



| 文件 | 作用 |

|---|---|

| `base.yml` | 基础编排：数据面只在 internal 网络内可达 |

| `local-ports.yml` | **叠加文件**：把数据面端口发布到宿主，仅供 dev/test |



预发布与生产**不叠加** `local-ports.yml`，因此不暴露宿主端口 ——

与 `environments.exposes_host_ports`（staging/prod 为 `False`）一致。

端口用变量引用（`${POSTGRES_PORT}` 等），所以自动跟随各环境的配置。

既有测试（`test_network_zones.py`）也在校验这两个文件的三层网络隔离。



### 49.2 真缺口一：`API_PORT` 没被守



第 48 节补的环境文件守护里，我列了 PostgreSQL 端口、Redis 端口、库名、存储根、Wiki 根，

**唯独漏了 `API_PORT`** —— 而它同样被 `local-ports.yml` 引用。



现状核对下来是对的（8400 / 8401 / 8402 / 8403，与声明一致且互不相同），

但改成别的值不会变红。已纳入两条守护。



### 49.3 真缺口二：compose 引用而 env 文件没提供的变量



**compose 对未定义变量的处理是静默替换成空串。**



于是 `${API_PORT}:8000` 会变成 `:8000` ——

配置错了却不报错，直到起容器时才发现（或更糟：起在了意料之外的端口上）。



补一条守护：从 `local-ports.yml` 里解析出**全部** `${VAR}` 引用，

要求四个 env 文件**逐个提供**。往后往 compose 里加新变量而忘了写进 env 文件，会立刻变红。



### 49.4 复验与一处顺手改善



从 `.env.prod` 删掉 `API_PORT` 复验：三条守护同时报错。

但两条报的是**裸 `KeyError: 'API_PORT'`**，

**不告诉你是哪个文件缺的** —— 四个环境里排查要多跑几轮。

顺手加了 `_need(data, key, where)` 辅助函数，现在报的是

「`.env.prod 缺少必需变量 API_PORT`」。



> 守护写对了还不够，**报错信息也要能直接指出病灶**，

> 否则它只是「红了」，而不是「说清楚了」。



### 49.5 一条可复用的教训



> **变量引用是延迟绑定的，因此「缺一个」不会当场报错。**

> 凡是模板里用 `${VAR}` 的地方（compose、CI、Dockerfile），

> 就要有一条「模板引用的变量，供应方是否都提供了」的守护。

## 50. CI 的**有意排除**也要有登记

### 50.3 第三条守护第一次是**误报**

## 52. 输入风控闸门：防虚假信息与编码混淆



### 52.1 需求与边界



用户指令：「做好风控（不能被用户以虚假信息或者 base 代码混淆）」。



**这是计划书未定义的一项**，已登记台账 **U41**（开源借鉴，仅借设计不引代码）。

计划书表 6 只规定了五层路由，未涉及输入侧风险筛查。



**关键约束：不得新增路由层。** 五层链路已由【八】冻结，

因此风控做成**前置闸门**，在进入五层之前判定，结论只有三档：



| 结论 | 含义 |

|---|---|

| `ALLOW` | 放行，原样进入五层路由 |

| `TAINT` | 放行，但标记「不可信」：可对话，**不得直接沉淀为事实** |

| `BLOCK` | 拒绝，本次业务不进入路由 |



### 52.2 编码混淆（「base 代码」）



对策是**先解码、再重扫**，而不是只扫一遍原文：



| 编码 | 处理 |

|---|---|

| base64 / base64url | 解出可打印文本后重新扫描 |

| 十六进制（含 `\xNN` 形式） | 同上 |

| 百分号编码 | 同上 |

| Unicode 转义（`\uNNNN`） | 同上 |



三条硬边界：**深度上限 3 层**（防递归炸弹）、**单层最短 16 字符**（防误报）、

**输入长度上限 20000 字符**（防超长载荷拖垮服务）。



判定口径：



- 解出**越权指令** → `BLOCK`（强信号，且是最危险的一种）；

- 解出的只是普通文本、无越权指令 → `TAINT`（**编码本身即可疑**，不得作为事实依据）；

- 没有任何编码 → 进入明文规则。



### 52.3 虚假信息



**不判真假，只判可信度。** 程序没有能力判定真伪，硬判只会制造新的错误。

本闸门只回答一个问题：**这条输入能不能作为事实依据。**



被标 `TAINT` 的情形：声称「已确认 / 官方证实」但未给证据、绝对化断言、

以「据内部消息」替代来源、以个人声明替代证据。



**有证据位则免除**：出现 `http(s)://`、`doi:`、`来源：`、`文件：`、`附件` 等可核验线索时，不打不可信标记。



下游怎么用：P6 质检与 Agent-Wiki 证据链据此决定能否入库 —— 

不可信输入可以参与对话，但**不能直接变成 Claim 事实**。



### 52.4 接入点与不变量



闸门接在 `IntentRouter.route()` 的最前面（默认开启，可传 `guard=None` 关闭）：



- `BLOCK` → 抛 `InputGuardError`，不进入任何路由层；

- `TAINT` → 记入 `notes`（「风控: 输入标记为不可信（…）」），供下游读取。



一条专门的测试守住「**闸门不是第六层**」：

`test_guard_is_not_a_routing_layer` 断言 `router.LAYERS` 仍是 5 项且不含 guard 字样。



### 52.5 图级别的接线（这一节是被漏掉过一次的）

第一版只把闸门接进了 `IntentRouter.route()`，却**没有处理它抛出的异常** ——
而 `scheduler/graph.py::_node_route` 是直接 `await self.router.route(...)`。
后果：**恶意输入会把整个 Graph 抛崩**，而不是礼貌拒绝。

这与计划书对「会话失效」的口径不一致 —— 那里是**返回状态、终止流程**，不是抛异常。

修法很干净：`_node_route` 捕获 `InputGuardError`，返回**不带 intent** 的状态。
图的分支函数 `_branch` 在「没有 intent」时本来就走 `NODE_TERMINATE`，
所以**不新增节点、不改边**，恶意输入自然落到礼貌终止。

补了 4 条图级测试：礼貌终止、子 Agent 零调用、编码载荷端到端拦截、正常请求不受影响。

> **教训**：把新能力接上主链路时，除了「调用点对不对」，
> 还要问「**它失败时会发生什么**」—— 失败路径没接好，等于给主链路埋了一颗雷。

### 52.6 TAINT 算完就丢 —— 约束形同空话

第二处被漏掉的是**结论的去向**。

闸门判出 TAINT 后，把说明写进了 `RouteDecision.degradation_notes`。
而 `graph.py::_node_route` 只在 `require_clarification` 分支里回写这个字段 ——
**正常流程下它被整条丢弃**。于是没有任何下游能知道「这条输入已被标为不可信」，
「不得直接沉淀为事实」就成了一句没人执行的话。

修法：给 `RouteDecision` 与 `GraphState` 各加一个**显式字段** `input_untrusted`，
由 `_node_route` 落到状态，并由 `SchedulerResult` 暴露给调用方。

**并且它必须受保护**：已列入 `PROTECTED_STATE_FIELDS`。
实测中真正先拦下「子 Agent 试图把它改回 False」的是**写作用域校验**
（P4「仅写入自有字段」），`PROTECTED_STATE_FIELDS` 是第二层 —— **两层防护**。

补 3 条测试：TAINT 结论落到最终状态、正常输入不被误标、子 Agent 洗不白。

> **教训**：算出结论 ≠ 约束生效。
> 凡是「A 判定、B 执行」的约束，都要有一条测试证明**B 真的收到了 A 的结论**。

### 52.7 终于有人执行：不可信事实只能落成 SUSPECTED

前两节修完之后，`input_untrusted` 能传到状态和结果了 —— 但**没有任何代码读它**。
全项目 grep 下来，它的引用只有「定义、传递、保护、测试」，**零消费者**。
也就是说：判定 → 传递 → 无人执行，约束只是又往后挪了一格。

本轮把消费者补上，收口点是 `agents/facts.py::FactWriter` ——
计划书要求的「子 Agent 产出事实的唯一出口」。

| 情形 | Claim 状态 |
|---|---|
| 可信输入 | `TRUE`（默认） |
| **不可信输入** | **`SUSPECTED`（待核实）**，并打 `untrusted_input=True` 标记 |

**为什么不直接拒绝写入**：页面留着才能被人工复核，直接丢弃等于把线索也扔了。
降为 `SUSPECTED` 既满足「不得**直接**沉淀为事实」，又不丢信息 ——
本体（`CLAIM_STATUSES`）本来就有这个状态，不需要自造。

三个写入点全部接上：mops、p8_payment、planner。

### 52.8 「能不能写公共库」由调用方一个参数决定

顺着风控再往下查一层：用户能不能把虚假信息写进**公共 Workspace**？
若能，被污染的是**所有用户**看到的知识库，比单条对话被误导严重得多。

查下来的结论是：**当前没有用户可触发的公共写入路径。**

| 位置 | 情况 |
|---|---|
| material_center/materials.py | 系统采集流水线归档 SOURCE 页，不来自用户 |
| p6_content_qa.py | 实际**传了** user_id，写的是私有 Vault（先前 grep 只截到首行，误判） |

但**这个保证没有任何机制守着**：

| 调用 | 落点 |
|---|---|
| `write_page(page, user_id='u-1')` | vault/u-1/ 只有本人可见 |
| `write_page(page)` | workspace/ **所有人可见** |

也就是说，以后谁新加一处漏传 user_id 的写入，**没有任何既有测试会变红**，
而后果是全体用户看到虚假信息。

修法与第 43 章处理 CI 脚本同型：把「允许写公共库」变成**显式白名单**。

新增 `tests/test_public_workspace_writes.py`，用 AST 扫出所有**没传 user_id 的**
`write_page` 调用，凡不在白名单里的立刻变红；并反过来检查白名单条目是否已失效。

造一处新的公共写入复验：

```text
E  AssertionError: 以下位置在写公共 Workspace（没传 user_id），但未登记理由：
```

豁免理由必须正面回答「内容是否来自用户」—— 判据就在这一句上。

### 52.9 文档里的数字也是断言

收尾时全文核了一遍计数表述，抓到一处过期数字：

| 位置 | 文档写的 | 实际 |
|---|---|---|
| 全场景用例库条数 | 397 条 | **463 条** |

用例库从 397 涨到 463 的过程中，`统一架构规范文档` 一直写着 397 ——
**没有任何测试会因此变红**，读者看到的是一个过期的数字。

这与第 44 章那次（文档说「待办」而代码早已做完）是同一类问题：

> **文档里的数字也是断言。** 既然「写错了数字」会误导人，它就该和「写错了结论」一样被机检。

已把 397 更正为 463，并加一条守护：`test_documented_case_count_matches_reality`
从文档里抽出「全场景用例库：N 条」的 N，与 `len(default_library().cases)` 比对。
把文档改回 397 复验：

```text
E  AssertionError: 文档写 397 条，实际 463 条
```

| 2 | 未登录只能文字，登录后才有语音 | **U64** | 访客层（不是免鉴权白名单） |
| 3 | 声纹识别 | **U63** | 服务端 CAM++，192 维 |
| 4 | 检索分类 + 工具选择 | **U66** | 10 类查询 → 工具序列真值表 |

### 53.1 先把「谁在哪算」定死，再谈实现（U65）

上一节（31.2）里 ASR/TTS 写的是「需模型」。补实现的第一步不是下载模型，
而是**先决定模型放哪边** —— 这个决定错了，代码怎么写都别扭。

| 组件 | 落点 | 模型 | 体积 | 为什么 |
|---|---|---|---|---|
| VAD | **端侧随包** | `silero_vad.onnx` | 1.7 MB | 「随时打断」要**毫秒级**。走网络往返 100 ms 起，体验上就从「打断」变成「等它说完」 |
| ASR | **云端** | streaming-zipformer-zh-14M (int8) | 24.2 MB | 端云分层已冻结：识别/合成/路由/质检全在云端 |
| TTS | **云端** | VITS-zh-ll | 126.9 MB | 同上；且 127 MB 塞进 APK 不现实 |
| 声纹 | **云端** | 3D-Speaker CAM++ | 27.0 MB | 属于「识别」，且要与账号绑定，必须在可信侧 |

合计约 180 MB，但**端侧只背 1.7 MB**。这正是分层的实际收益：
端侧保持轻，能力仍在云端。

模型用 `scripts/download_speech_models.py` 落地（`--only` 可单拉）。来源是
`hf-mirror.com`——`github.com` 本机不通，`modelscope` 的 API 返回 404，
镜像站是唯一可行路径。**下载完不是「文件在就叫成功」**：`SpeechModelPaths.presence()`
逐个组件报告「缺哪个文件、该跑哪个脚本」，避免只看到一个目录就以为齐了。

跑出来的真实数字（不是模拟）：

| 能力 | 实测 |
|---|---|
| VAD 切分 | 5.6 s 音频 → 3 段（1.248 / 1.088 / 1.728 s） |
| ASR | 「对我做了介绍那」（中文识别正确） |
| TTS | 5 个说话人；加载 0.7 s，合成 39943 采样（2.5 s）耗时 0.70 s |
| 声纹 | `dim=192`；同一人不同长度 `cos=0.7916` |

三处工程处理值得记下来：

1. **懒加载 + 单飞**：`SpeechRuntime` 用 `threading.RLock()` 包住初始化。
   并发首请求不会各自加载一份 127 MB 的 TTS 模型。
2. **音频解码只认一种**：`decode_wav` 只接受 16 bit PCM 单/双声道，
   其他格式**明确报错**而不是猜。`resample` 用线性插值，代码里如实标注了它的局限
   （高频会有混叠），没有假装是高质量重采样。
3. **流式喂帧**：`segment()` 按 512 窗口逐帧喂再 `flush()`，
   而不是整段塞进去 —— 这样端侧与云端的切分口径一致。

### 53.2 未登录只能文字：访客是「一种身份」，不是「不鉴权」（U64）

这里有个容易走偏的做法：把未登录请求从鉴权中间件里放行。**没有这么做**，
因为一旦「放行」，后面每个接口都要各自判断「这个请求到底是谁」，判断迟早会漏。

改成**访客层**：

| 设计点 | 做法 |
|---|---|
| 身份来源 | `POST /api/session/guest` 签发凭据：**1 h 期限 + 30 次额度** |
| 鉴权路径 | 与成员**同一套** `SessionAuthMiddleware`；`PUBLIC_PATHS` 只多这一个签发接口本身 |
| 层级派生 | 从**会话身份**（`guest:` 前缀）推出，**不采信请求体**——否则客户端能自己声明是成员 |
| 能力矩阵 | `AccessTier × Capability` 的**单表**，访客只有 `{text_query}` |
| 失败方式 | **fail-closed**：表里没登记的能力直接 `KeyError`，不是「默认允许」 |

`app.py` 里注册的 `AccessDenied` 处理器统一转 403，错误码 `capability_required`，
并带 `need_tier="member"`。实测访客链路：

```text
guest   200  {'tier': 'guest', 'capabilities': ['text_query'], 'text_query_budget': 30}
profile 200  guest 剩余 30
asr     403  capability_required / voice_input
plan    200  identity_lookup -> [structured.lookup, retrieval.hybrid_rerank]
chat    200  accepted / plan / chunk×N（SSE）
```

「两端」在实现上是同一份规则的两个副本：服务端 `access.py` 与
移动端 `access_policy.dart`（`kTierCapabilities`）。移动端这份**不是为了拦截**
（客户端拦不住人），而是为了**不把按不动的按钮画出来**。两端都 fail-closed：
`AccessProfile.fromJson` 解析失败时退回**访客**而不是成员。

首屏也因此改了：不再把登录页当第一屏。启动时先恢复成员会话，否则直接领访客凭据进对话页，
登录入口常驻在对话页上。

### 53.3 声纹：取不到分数就算不匹配（U63）

最危险的不是阈值调错，是**分数缺失被当成通过**。所以判据只有一条铁律：

```text
score is None  ->  matched=False
```

另外两条：

* **只存 embedding，不存音频**。声纹是 192 维向量，原始录音一律不落盘。
* 每账号最多 3 条样本，比对取**余弦最大值**；坏档**不静默清空**——
  悄悄清掉等于「用户下次发现自己要重新录入，且不知道原因」。

实测：同人不同长度 `cos=0.7916`，`verify(alice)=True`、`search→alice`、`verify(bob)=False`。
阈值 0.35 可配（`VOICEPRINT_THRESHOLD`）。

### 53.4 检索侧：十类分类 + 工具序列（U66）

原来只有三档路线（U46 冻结的 `RULE_DIRECT` / `HYBRID` / `LLM_ANALYSIS`），
但路线只回答「要不要过模型」，没回答「**具体用什么查**」。补的是后者。

十类查询，每类绑定一条工具序列（`CATEGORY_TOOLS` 是唯一真值表）：

| 分类 | 工具序列 |
|---|---|
| `identity_lookup` | `structured.lookup` → `retrieval.hybrid_rerank` |
| `fact_question` | `retrieval.hybrid_rerank` → `model.direct` |
| `policy_rule` | `retrieval.hybrid_rerank` → `vault.search` |
| `procedure` | `retrieval.hybrid_rerank` → `index.bm25` |
| `comparison` | `retrieval.hybrid_rerank` → `model.direct` |
| `recommendation` | `retrieval.hybrid_rerank` → `model.direct` |
| `personal_recall` | `vault.search` → `retrieval.hybrid_rerank` |
| `small_talk` | `model.direct`（**不检索**） |
| `multi_intent` | `clarify.ask`（**先问清**） |
| `unknown` | `retrieval.hybrid_rerank` → `model.direct` |

三个刻意的设计：

* **只消费，不改写**：planner 读三档路线的结论，不重新判定路线。五层意图路由与三档路线
  都已冻结（【八】/U46），这一层不新增第六层、也不动既有两层。
* **按 tier 裁剪**：访客请求里带 `vault.*`/`business.tool_call` 的工具会被裁掉，
  并登记在 `dropped_tools` 里**写明理由**——不是悄悄消失。裁剪后若序列为空，降级为 `model.direct`。
* **`policy_rule` 无证据就弃答**：制度类问题查到空结果时不给「大概是这样」，
  直接 abstain。`small_talk` 走 `model.direct` 不做检索，省一次无意义召回。

`bypasses_llm` 只看**第一步**（首步是 `structured.lookup` 就说明不需要模型），
`may_use_llm` 看任一步。「精确标识直查不过模型」这条（U46）因此落到了具体工具上。

对话侧 `ChatOrchestrator.stream()` 的 SSE 事件契约：
`accepted → plan → chunk* → [revise] → done`。
其中 **`revise` 是覆盖不是追加**——复检（U47）改写查询后重出的答案要替换前文，
客户端把它当追加就会看到两段互相矛盾的答案。

### 53.5 顺手抓到两个真实缺陷

补 VAD/ASR 时把端口对上，才发现 P7 的「随时打断」一直是死代码：

1. **采样从来没喂给 VAD 和 ASR**
   `VoicePipeline.captureUtterance()` 订阅了麦克风，但没把帧转发给 `VadPort.feed()`
   （这个接口**此前压根没有**），也没喂给 ASR。于是 VAD 永远认为没声音、
   ASR 永远认不出字。已补 `VadPort.feed(List<double>)` 与 `AsrPort.finish()`，
   现在同一路采样同时喂 VAD 与 ASR。
2. **TTS 失败把整轮对话判成失败**
   文字已经渲染出来了，只因为合成没成功就整轮标红。已改成降级为 warn——
   声音没了，回答还在。

顺带补了一个 `PipelineEventKind.voiceNoSpeech`：**「没说话」和「出错了」不是一回事**，
合成一个状态会让用户以为麦克风坏了。

### 54.1 账号标识为什么存两份（U67）

手机号/邮箱既是登录凭据又是 PII，两个需求是**冲突**的：

* 要能用它登录 → 必须能按它查人 → 得**可检索**；
* 不能让人拖库拿到 → 必须**不可还原**。

一个字段同时满足不了，于是拆成两列：

| 列 | 算法 | 性质 | 用途 |
|---|---|---|---|
| `ident_digest` | HMAC-SHA256（服务端密钥） | 可查、不可逆 | `WHERE` 定位账号、判重复注册 |
| `ident_cipher` | Fernet（AES-CBC + HMAC） | 可还原、不可查 | 服务端核对、脱敏展示、发送通知 |

只用密文：每登录一次都要全表解密，O(n) 且密钥使用面最大化。
只用摘要：服务端自己也不知道用户填的是哪个号，发通知、人工核验全部做不了。
两列都有，各自只干自己那份活。

三条配套的「不装样子」：

1. **不可枚举**。账号不存在与密码错误返回**同一个 code、同一句 message**；
   找回接口对「存在 / 不存在」的响应结构完全一致。否则注册接口就成了批量探测
   手机号的工具。
2. **时序也不泄漏**。`AccountStore.__init__` 里**预生成**一个 `_dummy_hash`，
   账号不存在时用它跑一次 bcrypt 校验再返回。为什么不每次现算：现算等于给攻击者
   一个「打不存在的号更贵」的 DoS 入口 —— 每条请求都让你花 100 ms 的 CPU。
3. **昵称长度是近似值**。`grapheme_length()` 把组合符、变体选择符、ZWJ 并进前一字素，
   但它**不是完整的 Unicode 字素簇算法**，函数名与文档都写明「近似」，
   而不是假装数得准。

登录失败 5 次锁 15 分钟，锁定期内**密码对了也不放行**（否则爆破只要不连续就绕过）。

### 54.2 忘记密码：令牌只存摘要，通道可插拔（U68）

| 环节 | 做法 | 为什么 |
|---|---|---|
| 令牌生成 | 32 字节 `secrets.token_urlsafe` | 160 bit，不可猜 |
| 存储 | 只存 SHA-256 摘要 | 拖库也拿不到能用的令牌 |
| 有效期 | 15 分钟 | 够走完流程，不够被慢慢利用 |
| 状态机 | 待用 → 已用 / 已废，**单向** | 二次使用、过期后复活都拒绝 |
| 改密后 | `force_logout` 吊销该账号**全部**会话 | 「改了密码但小偷还开着」是最坏的结果 |

通道是端口（`ResetChannel`），不是 if-else：

* `DevChannel`：令牌**进响应体**，供本机联调；`dev_token_visible()=True`；
* `ConsoleChannel`：只打 stdout，不在响应里回显；
* `build_channel(name, environment=)`：**production 环境只允许 `smtp`**，其他一律
  `unsafe_reset_channel`；`smtp` 则抛 `channel_not_configured`。

最后一条意味着**当前部署的找回功能在生产环境是不可用的** —— 本仓库没有邮件凭据。
这不是缺陷隐瞒，是接口如实返回「未配置」。反过来，若允许 `dev` 进生产，
重置令牌就会出现在 HTTP 响应里，等于谁都能改任何人的密码。

### 54.3 昵称：可以随机，但不做全局唯一（U69）

随机昵称由 `_ADJECTIVES × _NOUNS` 组合，随机源可注入（测试才可复现）。
三条边界：

* **不做全局唯一**。昵称不是标识，唯一性会把「重名」变成注册失败，
  逼用户在注册第一步就想名字 —— 而用户的诉求恰好是「不想想名字也能注册」。
* **`None` 与 `""` 不是一回事**。`register()` 写成 `if nickname:` 时，
  空串被当成「没提供」而静默生成随机昵称；接口层却认为「用户填了空」该报错。
  这是测试抓出来的真 bug（`test_invalid_nicknames_are_rejected[空]` DID NOT RAISE），
  改成 `if nickname is not None`。
* **词表只在服务端**。端侧「随机一个」走公开接口 `/api/accounts/nickname/suggest`，
  不在 Dart 里再拼一份。两处词表的必然结局是「端上能填、提交报非法」。

随机刷新有频控（3 次/分钟），超了报 `too_many_requests` —— 否则它就是一个
免费的写接口。

### 54.4 自选模型：三档目录 + 归属校验（U70）

| 档 | 例子 | 凭据来自 | 计量 |
|---|---|---|---|
| `free` | 本机 `qwen2.5vl:3b`（ollama） | 无需凭据 | 50 次/天/账号 |
| `trial` | 平台限免 `deepseek-chat`，到期 2026-12-31 | 平台 `DEEPSEEK_API_KEY` | 100 次/天/账号 |
| `byok` | 用户自填 base_url + model + key | **用户自己的 key** | 不占平台额度 |

「默认免费」是用户原话，所以未绑定时走 `_match_by_profile()`：
`vision` → `long_context` → 免费档优先，`matched_by` 字段把「命中哪条规则」写出来，
不是黑箱。过期的限免模型**直接消失在目录里**，而不是「列出来、点了报错」。

「不会在未经人允许下被盗用」这句话，落成四处代码：

1. **凭据按账号隔离**：`ModelBinding.user_id` 必须等于请求者，
   `resolve()` 里 `if binding.user_id != uid: raise ModelAccessError("forbidden")`；
2. **key 只存密文**：`FieldCipher` 加密落盘，`ModelBinding.public_view()` **不含密文字段**，
   接口只回 `sk-****cdef` 掩码，**没有任何回读路径**；
3. **`ResolvedModel.__repr__` 自藏 key**：`repr` 常被顺手打进日志，不能指望调用方记得脱敏；
4. **按调用传参**：`chat/stream(..., provider=, api_key=, base_url=)`。
   显式指定 provider 就**只走它、不降级** —— 静默换成另一个模型，和盗用一样，
   都是用户没同意的事。

#### 本轮跑测试才发现的真缺陷：默认路径不计量

`./pytest` 里 `test_chat_consumes_the_users_model_quota` 挂了。原因不是接口没接上，
而是 `_default_for()`（未绑定用户走的那条路）**从不 `consume()`**。

后果比这条测试严重得多：新用户从没选过模型，每一次对话都走默认路径，
所以「免费 50 次/天」对**最该被限流的账号群体**是一句空话 —— 而免费额度
同时是防滥用与限免到期的唯一闸门。

修的时候顺带把顺序也摆了：**先确认平台凭据，再扣额度**。原来的顺序是
「先扣、再发现没配 `DEEPSEEK_API_KEY` 然后报错」，等于平台配置失误也让用户
当天少一次额度。这条改动同时作用于已绑定平台档与默认档，两处口径必须一致，
否则「同一件事两个答案」比任何一边单独错都难解释。

#### 画像必须能改，否则「按画像匹配」只在注册那一刻成立

匹配规则读的是账号的 `prefs`，但当时**没有任何接口能改它**，注册表单也不收集 ——
于是默认模型永远是「免费档里的第一个」，所谓「按个人信息匹配」只剩一句注释。
补了 `POST /api/accounts/prefs`，并加一条容易被忽略的护栏：

> 回给界面的「现在会匹配到哪个模型」必须用 `preview_default()` 算，
> **不能用 `resolve()`** —— 后者会 `consume()`。界面每保存一次偏好就扣一次额度，
> 用户光是改标签就能把免费次数点光。`test_prefs_update_does_not_burn_the_free_quota`
> 盯的就是这条。

### 54.5 定位、推荐与导航（U71）

**坐标系是三套，不是一套。** GPS 出 WGS84，高德/腾讯要 GCJ-02，百度要 BD-09。
直接把 WGS84 拼进高德链接，偏差几十到几百米 —— 用户到了地方发现不对，但没人知道
是坐标问题。

| 转换 | 有闭式解 | 实现 |
|---|---|---|
| WGS84 → GCJ-02 | 有（公开偏移算法） | 直接算 |
| GCJ-02 → WGS84 | **没有** | 两次迭代逼近，误差 < 1 m |
| GCJ-02 ↔ BD-09 | 有 | 直接算 |
| 境外坐标 | — | 原样返回（`_out_of_china`），GCJ-02 只在中国境内偏移 |

**定位粗化按位截断，不是四舍五入。** 截断会把同一格里的点压到格子内，
四舍五入会把它们往格子角上挤 —— 那个角本身就是个「假热点」。
默认 3 位小数（≈110 m），端侧 `ApiClient._coarsen()` 与服务端 `privacy_grid()`
**同口径各做一次**。为什么两端都做：端侧可能被绕过（改包、直连），
服务端可能被信任过度（以为端上一定做过）。

**导航链接本地生成，起点默认不传。**

| 目标 | URI | 坐标系 |
|---|---|---|
| 高德 | `uri.amap.com/navigation` | GCJ-02 |
| 百度 | `baidumap://map/direction&coord_type=bd09ll` | BD-09 |
| 腾讯 | `apis.map.qq.com/uri/v1/routeplan` | GCJ-02 |
| 兜底 | 高德网页版 | GCJ-02 |

起点留空让导航 App 自己取「我的位置」：**我方坐标不外传**，且用户看到的是
App 自己那颗蓝点，不会出现「起点偏了一条街」这种无从解释的错。

三件当前**做不到**的事，界面直接说，不画一个假地图：

| 缺口 | 表现 | 原因 |
|---|---|---|
| 地图底图 | `map_available=false` + 红字 `map_note` | 没有地图服务 key |
| 真实 POI | `data_source="seed-demo"` + 界面「示例数据」角标 | 没有 POI 数据源 |
| 地址反查 | 不提供 | 同上（反查也要 key） |

`places.json` 解析失败时抛 `places_unreadable`，**不静默退回示例**：
悄悄换成示例数据，用户会以为推荐结果是真的。

### 54.6 端侧接线：四个页面与一处「单向门」

| 文件 | 职责 |
|---|---|
| `ui/login_page.dart` | 四态一页：登录 / 注册 / 找回 / 设置新密码；手机号↔邮箱切换 |
| `ui/account_page.dart` | 脱敏标识、改昵称、随机刷新、改密、三档模型选择、BYOK 接入/解除 |
| `ui/location_page.dart` | 坐标卡片、偏好筛选、带 `reason` 的推荐、四家导航跳转 |
| `main.dart` | 把上面三个页面接到 `ApiClient` 上，并按能力决定入口是否出现 |

`main.dart` 这轮有三处结构性改动，外加一处错误语义收口：

1. **`_login` 拆成四个**：`_loginWithKind` / `_register` / `_forgot` / `_reset`。
   原来只有一个 `(account, password)`，装不下「带 kind 的登录」「注册要昵称」
   「找回要回令牌」「重置要令牌+新密码」四种语义。
2. **`_teardownMember()` / `_signOut()` / `_relogin()` 三分**。登出的出口是
   **访客态**；改密的出口与「会话失效→重新登录」的出口都是**登录页**
   （必须重新输密码）。共用一个方法的结果是：用户点了「重新登录」，
   却落到访客对话页 —— 他刚被告知要重登，看到访客模式只会再点一次。
3. **登录页加了退路（`onSkip`）**。登录页在 login 模式下本来没有返回箭头，
   访客点「登录」后就只剩注册一条路 —— 这是标准的单向门。现在有 ✕
   与底部「先不登录，以访客身份继续」两条。

错误语义收口：账号/模型/定位这 15 个调用原来都走 `_guard`，于是注册失败会抛
`VoiceFailedException` —— **异常类型在说一件没发生的事**。新增 `_guardAccount()`：
401/403 仍交给 `_guard`（会话失效、能力不足、业务规则不满足是三件事），
其余非 2xx 统一抛 `AccountException` 并带上服务端 `code`。

另外两处容易被当成小事：

* `launchUrl` 在「没装这个 App」时**可能抛 `PlatformException` 而不是返回 false**
  （各家 ROM 不一致），所以 `try/catch` 与返回值两个失败面都要接住，
  否则用户点一下只会闪退到桌面。
* 对话页标题会显示昵称（`AI 管家 · 昵称`）。昵称改完要在**界面上看得到**，
  否则「改名成功」只是对话框里的一行字。改完返回对话页时会重新拉一次资料，
  拉不到就维持原样 —— 不拿「AI 管家」冒充用户的昵称。

### 54.8 这一轮踩到的坑

| 坑 | 现象 | 结论 |

| 测试共享 `storage_root` | 前 11 项 409 | 每个用例必须把 `storage_root` / `account_store_root` 指向 `tmp_path` |

### 54.9 真进程验收：`scripts/smoke_accounts.py`

`tests/test_accounts_api.py` 走 ASGI 直连，证明的是「路由装配对不对」。它证明不了
「进程起来、连上 Redis/Postgres、真的写进磁盘之后还能不能用」——而那才是用户会遇到的那一层。
所以另有一个走**真 TCP** 的验收脚本：

```

    ai_butler.server:build_app --factory --port 8411
.venv/Scripts/python.exe scripts/smoke_accounts.py http://127.0.0.1:8411
```

八段 45 项，逐条对应需求原话（注册与隐私 / 昵称 / 自选模型 / 定位推荐导航 /
默认免费模型 / 会话与口令 / 访客越界 / 落盘检查），**实测 45/45 通过**。三条只有真进程才验得到的结论：

1. **默认免费模型真的能答，且真的扣额度**：`/api/chat/stream` 出 `accepted → plan → chunk*`，
   回答非空，`free_remaining` 由 50 变 49。这条把 U70 里「免费额度不是白调」从代码事实变成运行事实。
2. **落盘是密文**：`data/dev/storage` 下 5 个 json 全文检索，既没有明文手机号，也没有三个口令。
3. **能力矩阵在进程上生效**：访客拿 `/api/models` 与 `/api/location/recommend` 都是 403，
   不是「界面上藏起来」。

这一轮正是被它拦下来的。

### 54.10 找回密码的真投递：SMTP 通道（U72）

U68 当时只留了端口，`smtp` 直接抛 `channel_not_configured` —— 结果是
**邮箱注册的账号在生产环境根本没法自助找回**。这一轮把通道补成真实现。

| 决定 | 为什么 |
|---|---|
| 只用标准库 `smtplib` | 发一封重置邮件不该把项目绑到某家邮件服务商；465 走 `SMTP_SSL`、587 走 STARTTLS |
| `deliver(kind, masked, token, destination)` | 通道必须知道**真地址**才发得出去，但日志里只许出现 `masked`。两个参数分开传，谁也替不了谁 |
| 投递失败**不抛**给调用方 | 一抛，「账号存在 + 投递失败」和「账号不存在」的响应就不一样了 —— 不可枚举当场被撕开一个口子。失败进 `failures` 给运维看 |
| 手机号账号不硬发 | 没有收件地址就记一条 skip，不静默假装发过 |
| 缺配置启动即拒 | 报出**缺的是哪个键**（`host`/`port`/`sender`），不许带着半个配置上线 |

**如实登记的缺口**：手机号注册的账号没有邮箱，SMTP 救不了它。要覆盖这部分用户需要
短信通道（阿里云/腾讯云短信，需账号、签名与模板审核）。本仓库**不接**第三方短信 SDK ——
凭据到位后按同一个 `ResetChannel` 端口实现即可，接口层不用改。

当前可用的三种组合：

| 环境 | `RESET_CHANNEL` | 效果 |
|---|---|---|
| dev / staging | `dev` | 令牌进接口响应，本机联调闭环 |
| 自建无凭据 | `console` | 令牌打服务端 stdout，人工转发 |
| production | `smtp` | 真发邮件；**其余取值启动即拒** |

少一样凭据都不算「解决」。所以这一块**要用户提供**：一个能发信的 SMTP 账号
（QQ / 163 的授权码即可），或一家短信服务商的签名与模板。细节见 §54.12。

### 54.12 需要外部提供才能落地的东西

这一节是**给决策者看的清单**：哪些是「代码已经写好、只差一把钥匙」，哪些是「真的还没写」。
每条都写清「现在的如实表现」，不是为了免责任，是为了让界面上的每一句提示都有出处。

| 短信签名 + 模板（阿里云/腾讯云） | **手机号**账号自助找回 | 手机号账号走 smtp 只记一条 skip；只能用 `console` 人工转发 | 按 `ResetChannel` 端口加一个 `SmsChannel`，接口层不动 |

| 平台模型的**正式**付费 key | 限免档的真实额度与成本 | 本机 `.env.dev` 用的是自己的那把 key；线上需另配 | 换环境变量即可；额度成本归属是运营决定，不是技术决定 |
| Android 真机（USB 调试授权） | P7 语音真机验收（唯一还 `implemented=False` 的阶段） | APK 与权限、随包模型已机检通过；无设备无法跑 | 接上真机后跑验收流程 |
| **正式签名密钥**（keystore + 两个口令） | 对外分发 / 上架 | `build.gradle.kts` 的 release 仍签 debug key（Flutter 模板默认，带 TODO） | 换 `signingConfigs.release` 并把口令放 CI secret；**同一个包名换签名会导致老用户无法覆盖安装**，越早定越好 |

**为什么不先接短信 SDK**：短信要账号、签名与模板三样都过审才能发得出去，任何一个不到位都只能
"看起来接通了、实际发不出去"。这一层宁可先留端口 + 如实报错，也不做半吊子接通。

### 54.13 多轮上下文的接线与记忆隔离（U73）

**改之前的状态**：`scheduler/context.py` 功能完整（窗口 / 压缩 / 摘要 / 账号分片），
测试也全绿，但**全项目没有一个调用点**；`/api/chat/stream` 只读 `utterance`，
每轮发给模型的 messages 只有 `system` + `user`。端侧早就在 body 里传了 `session_id`，
但那是 `deviceId`，且服务端根本没读 —— 字段送到门口被静默丢弃。
结论：**绿灯亮着，多轮不存在**（MEMORY E-77）。

**现在的链路**：

```
body.conversation_id ──► 会话索引表（签发 / 归属校验）──► ContextManager.load
                                                              │
                                         历史窗口 + 摘要 ──► 提示词【对话历史】
                                                              │
                                         回答完成 ──► append_exchange（一问一答一次落盘）
```

**四道门**（全过才读写历史，任何一道不过都退化为单轮并把原因写进 `notes`）：

| 门 | 不过时 | 为什么这么设 |
|---|---|---|
| `chat_history_enable` | 「多轮记忆已按配置关闭」 | 关掉即是显式单轮，不是「悄悄忘了」 |
| 装配了 `context_manager` | 「会话上下文未装配」 | E-77：不装配也要说出来，不能装成新用户 |
| 层级是成员 | 「访客不读写对话历史」 | 访客原话属 PII；`guest:` 含冒号也不是合法目录名 |
| 有会话标识 | 「未提供会话标识」 | 不知道读哪一段，就不该猜 |

**隔离的三层**：

| 层 | 机制 | 挡住什么 |
|---|---|---|
| 物理 | 路径 `conversations/{user_id}/{conversation_id}.json` | 跨账号**物理不可读**（P4） |
| 索引 | 标识必须由服务端签发，归属写进 Redis 索引表 | 客户端自造标识、同账号串会话 |
| 校验 | 未签发 / 格式非法 / 归属不符 → 一律重签；后端异常 → 判「不是你的」 | 探测他人会话、异常放行 |

**落盘策略**（比「记住所有东西」更重要的部分）：

| 情形 | 是否落盘 | 理由 |
|---|---|---|
| 正常回答 | 是 | — |
| 复检推翻初稿 | 是，但存 `revise` 之后那一版 | 存初稿等于让下一轮把幻觉当「自己说过的话」引用 |
| 规则类弃答 | 是 | 用户确实看到了一句回答 |
| 多意图反问 | 是 | 反问是一个完整轮次，否则用户重述时模型不知为何重述 |
| LLM 失败 / 回答截断 | **否** | 「有问无答」比没有更坏：下一轮会重复回答或自行脑补 |
| 访客 / 未提供标识 | **否** | 不建会话就不该有历史 |

**指代消解只作用于检索侧**：句子短且含指代词（「它」「第二个」「还有呢」）时，
把上一轮**用户问题**拼进检索文本；**不改写 query 本身** —— 改写会让
「用户问了什么」与「检索了什么」对不上，复检与评测无从对齐。
整段历史拼进检索会污染 BM25（上一轮每个词都被当成本轮诉求），所以只取最后一句。

**装配断言**：抽出 `build_chat_orchestrator()` / `build_chat_context_manager()` 作为唯一装配点，
守护测试断言 `app.state.chat_orchestrator.context_manager is not None`。
「类有测试、链路没人构造」是绿灯下的空功能，只测类测不出来 —— 这条断言比再写十个
`ContextManager` 用例更有用。

**已知边界（如实登记）**：
- 摘要是**抽取式**的（保留每轮开头，不编造）。换大模型摘要要额外计一次额度，
  且要防「摘要引入不存在的结论」，暂不默认开启。
- 换话题时历史仍会进提示词（窗口内）。端侧已提供 `startNewConversation()` 主动开新段，
  自动判「话题漂移」属于需要评测校准的能力，不在这里拍脑袋做。
- 上下文按文件落盘，单次读写是同步 IO。文件量级是几 KB，当前规模可接受；
  真到高并发要换成异步存储端口，接口形状已经具备（`ContextManager` 只依赖 `FileStore`）。

### 54.14 五层意图路由的接线（U74 / U75）

**改之前的状态**：`scheduler/router.py` 里五个层类写得很完整，`test_scheduler_router.py`
也全绿 —— 但 `HardRuleLayer` / `VectorLayer` / `LLMFallbackLayer` 在 `ai_butler/` 内
**引用数为 0**，没有任何函数把它们组装成管道。所以「语义识别」实际跑的只有
`planner.classify()` 的正则那一档，Jev 与向量层从未启动。这是 E-77 的第二种形态。

**接的是三层，不是五层**（层数与顺序仍是表 6 的冻结值，只接有实现的）：

| 层 | 状态 | 原因 |
|---|---|---|
| L1 硬规则 | 接 | 正则**从 `planner.CATEGORY_SIGNALS` 派生**，表序即优先级，不另存一份（E-44） |
| L2 Jev | 接 | 云端 `deepseek-chat`；影子期走**旁路**（见下） |
| L3 向量 | 接 | 本地 `bge-small-zh-v1.5` + 100 句示例语料；懒加载 + 装配后预热 |
| L4 垂类模型 | **不接** | 全项目只有 `VerticalDecisionModel` 协议、**没有实现**；U03 要求先标定 |
| L5 大模型兜底 | **不接** | 与 L2 是同一件事（同网关、同 prompt 形态、同解析），接了两份账 |

**标签集 = `QueryCategory` 的 10 个取值**（解决【文档未定义项 #1】）。不另造一套意图标签，
路由结论才能**直接**被 `planner.plan()` 消费，不需要「路由标签 → 查询分类」的翻译表。

**路由只补空缺，不覆盖确定性结论**：`classify()` 先跑正则，全部落空时才采用路由标签。
反过来就是用「大概对」换掉「确定对」，而且同一条查询会时而查 A 时而查 B。

**兜底四级**（任一层异常只降级，不阻断）：

```
L1 命中 ─► 用正则结论
  └ 未命中 ─► L3 相似度 ≥ 阈值 ─► 用向量结论
        └ 未达阈值 ─► L2 Jev ─► 澄清? 暂停分发 : 用模型标签
              └ 失败/低置信 ─► 退回正则 UNKNOWN ─► hybrid_rerank ─► model.direct
```

**影子期必须旁路**（U75）。原实现的 `shadow_mode` 判在「决策拿到之后」，
模型仍被完整调用一次，而 `route()` 是 `await`、单层超时 5 秒 ——
「只记录不决策」在成本上等于「照常调用一次模型」，影子期给每个请求白加一次延迟
（云端实测 P50 2.3s）。现在影子态立即返回「不采信」，调用丢后台任务，异常一律吞掉。

**冷启动不在请求路径上**。实测加载模型 6.9s + 建 100 句索引 2.8s ≈ **9.7s**，而单层预算 5s，
所以「第一个请求顺手加载」必然撞超时。装配后立刻用守护线程预热；冷启动窗口内的请求
只等 0.5s 就降级，并把「向量层冷启动中」写进 `degradation_notes`。

**判定节点固定 `temperature=0`**（U75）。原先不下发该字段，各厂默认采样：
同一批 62 句连跑两轮，澄清数 16 → 20。判定不可复现，路由行为就无法回归、评测也无法比较。
生成类调用不受影响（未指定时不下发）。

**两处实现缺陷的实测修正**（E-78 / E-80 重判）：

| 缺陷 | 本地 `qwen2.5vl:3b` | 云端 `deepseek-chat` | 本仓库的取值 |
|---|---|---|---|
| E-78 截断 | 64 token 时 3/6 解析失败（复述候选标签被截断），256 后 6/6 | 64 token 也 62/62 全解析 | `JEV_MAX_TOKENS=256`：不是修 bug，是给弱模型留余量 |
| E-80 澄清 | 6 次澄清 6 次错，关掉后 69.4% → 79.0% | 20/62 要求澄清，**14 次标签本来就对（70%）**，其中 13 次集中在 multi_intent(7/7) 与 unknown(6/6) | `JEV_ALLOW_CLARIFY=true`（默认采信）；**弱模型请设 false** |
| E-79 置信度 | 恒 0.90~0.95，0.82 阈值形同虚设 | 0.20~0.98，中位 0.90；判对均值 **0.89** vs 判错 **0.72~0.74**，但 0.82 **只拦下 6/14 判错** | 阈值仍是【八】冻结的 0.82：有区分度，但拦不住「自信地理解错」 |

云端这 20 次澄清里，**6 次误报的形态完全一致**：模型把不认识的句子标成 `unknown`，
而 `unknown` 恰是合法的澄清来源，于是顺手举手。**澄清精确率 ≈ 1 − `unknown` 误判率**——
本地 3B 的 22.2% 与云端的 70%，差在 `unknown` 判得准不准，不在澄清机制本身。
另外，云端漏出阈值的那 8 条判错里有 5 条同属 `identity_lookup → fact_question`
（带单号/错误码/版本号的句子被当成普通事实问题）：这是**大类内部的混淆**，
一维置信度无从表达，只能靠 L1 的标识符正则。

**`temperature=0` 的边界**：固定温度后连跑两轮，**标签与澄清集合逐条一致**，
但 `≥0.82` 的计数在 50/51 之间、判对置信均值在 0.888/0.892 之间抖动（后端批量 + MoE 路由）。
所以要的是**行为可复现**而非浮点数可复现；守护测试断言标签与澄清决策，不断言置信度等值。

**实测（62 句自建语料 + 云端 deepseek-chat 作 L2）**：

| 拓扑 | 总准 | core | edge | L2 调用 |
|---|---|---|---|---|
| 现状（仅正则） | 66.1% | 76.0% | 25.0% | 0% |
| L1 + L3 @0.62（无 L2） | 79.0% | 86.0% | 50.0% | 0% |
| **L1 + L3 @0.62 + L2（本轮）** | **83.9%** | **92.0%** | 50.0% | 8.1% |
| L1 + L3 @0.80 + L2 | 80.6% | 92.0% | 33.3% | 16.1% |

L3 在 0.62 阈值下把 L2 的调用率从 30.6% 压到 8.1%，这 5 条里 L2 判对 3/3，
另外 2 条模型要求澄清（「明天天气怎么样」「有没有便宜点的」，按场景判为误报）。
**10 条错误里 8 条来自 L1**（「我的」抢占、「，」不在分句符、「然后」不在并列词、
「怎么样」被排除），说明下一个瓶颈是 L1 的覆盖与优先级，不是模型。

**方法论限制（读数字前必看）**：62 句太小（±6~8 个点，只能看排序）；标签是自标的；
L3 的示例语料与测试句同源，其成绩被高估；`intent_vector_threshold=0.62`
**不是标定值**（`VECTOR_THRESHOLD_CALIBRATED=False`，U03 未完成）。

> **本节数字是「优化前」的存档**。据此定位到瓶颈在 L1 之后，已在 §54.15 完成
> 一轮 L1 实测优化（单层 56.5% → 79.0%）并复测整条管道（83.9% → 91.9%）。

## 54.15 L1 实测优化与「评测 → 修复」闭环（U76 / U77）

§54.14 的结论是「下一个瓶颈是 L1，不是模型」。本节把那句话兑现，
并把「评测发现问题 → Harness 自我修改」这条缝接上。

### 一、L1：从 56.5% 到 79.0%

依据是 §54.14 那批 62 句的**逐条失败清单**（8 条误判 + 19 条漏判），
不是凭印象加正则。每一处改动都写得出语言依据：

| 病根 | 语言依据 | 改法 | 结果 |
|---|---|---|---|
| 裸「我的」抢占 | 「我的发票」「我的订单」里「我的」是**限定语**，指对象不指回忆 | 只认时间指代（我上次/我之前）与回忆动词（我说过/我提过） | 2 条纠正 |
| 是非问句无位置 | 「订单…能改收货地址吗」问的是**许可**，不是这条订单的状态 | 新增「能/可以 + 动作 + …吗（句末）」信号，**排在标识之前** | 2 条纠正 |
| 「怎么样才能」被连带排除 | 「怎么样」问状况，「怎么样**才能**」问步骤 | 单独放行，不再整类排除 | 1 条纠正 |
| 要素词缺口 | 多久 / 哪个快 / 给我个方案 / 便宜点 / 在哪开 | 补进事实、比较、推荐、步骤四类 | 7 条纠正 |

| 指标 | 改前 | 改后 |
|---|---|---|
| L1 命中（非 unknown） | 43/62 = 69.4% | **53/62 = 85.5%** |
| L1 判对 | 35/62 = **56.5%** | **49/62 = 79.0%** |
| core 覆盖 / 精确 | 72.0% / 91.7% | **86.0% / 95.3%** |
| edge 覆盖 / 精确 | 58.3% / 28.6% | **83.3% / 80.0%** |

**零回归**：原先判对的 35 条一条没被打错（逐条比对，不是只看总数）。

**刻意没改的一处**：裸逗号**不**作为多意图分句符。收进来能把
「这个多少钱，怎么付款」判对（+1），但会把「给我个方案，怎么部署内网服务」
判成多意图（-1）——后者是一个诉求加方案细节，反问一次等于白打断用户。
**净收益为 0 而体验明确变差，所以不改**，并由
`test_bare_comma_is_deliberately_not_a_multi_intent_separator` 钉住，
防止后人「顺手」加回来。

### 二、整条管道复测（云端 deepseek-chat 作 L2，逐句判定取自 §54.14 的缓存）

| 拓扑 | 改前 | 改后 | core | edge | L2 调用率 |
|---|---|---|---|---|---|
| 现状（仅正则 + unknown 兜底） | 66.1% | **88.7%** | 92.0% | 75.0% | 0% |
| L1 + L3 @0.62 | 79.0% | **91.9%** | 94.0% | 83.3% | 0% |
| **L1 + L3 @0.62 + L2** | 83.9% | **91.9%** | **94.0%** | 83.3% | **1.6%** |

L2 的调用率从 8.1% 降到 1.6%（62 句里只剩 1 句），说明 **L1 补好之后
模型基本没事可做**——这反过来印证了 §54.14 的判断：瓶颈是规则覆盖，不是模型。
剩余 5 条错误里 4 条仍在 L1（「你们的营业时间是怎么安排的」把「怎么安排」
当问步骤、「怎么退款；还有发票怎么开」两类同属 procedure 凑不出多意图、
「我的发票什么时候能开出来」、「这个多少钱，怎么付款」），1 条是 L2 澄清误报。

### 三、缺陷单：让「不通过」变成可处置的东西（U76）

`evaluation/defects.py`。报告只说「哪一维不过、证据是什么」，
缺陷单要说「哪一类、谁处理、从哪改、怎么复现」。三档处置：

| 维度 | 缺陷类别 | 严重度 | 处置 | 理由 |
|---|---|---|---|---|
| 安全与权限 | `security_violation` | blocker | **manual** | 自动改权限代码=让被评的缺陷改判据，改完测试绿了、漏洞还在 |
| 检索召回 | `recall_gap` | major | auto | |
| 证据忠实 | `missing_evidence` | major | auto | |
| 工具真实性 | `false_tool_call` | major | auto | |
| 稳定性 | `unstable` | major | auto | |
| 成本效率 | `cost_regression` | minor | auto | |
| 输出质量 | `quality_gap` | minor | auto | |

三个特例，都是「不能让工单池被噪声塞满」：

1. **无痕迹**产**一条** `no_data`，不产七条（埋点没接不是七个问题）。
2. **评测输入不全**记 `config_gap`（manual），不记系统缺陷：用例没给金标、
   只跑一次，这是评测方法缺口。为此在维度层补了结构化标记
   `DimensionResult.details["inconclusive"]`，缺陷层据**字段**分流，
   而不是匹配中文文案（文案一改判据就失效，且中文匹配就是 E-44 那类漂移源）。
3. **安全缺陷存在时整批阻断**自动处置：`auto_repairable()` 返回空。
   在会越权泄露余额的系统上优化召回率，是把力气花在错的地方。

### 四、受理：谁能进自动流水线（U77）

`harness/intake.py`，四道闸：

1. **只收 `auto`**，`manual` 直接拒收并写明理由（拒收不是失败，是正确处置）；
2. **安全缺陷存在时整批不受理**；
3. **命令只从登记表取**，不接受拼接——沙箱白名单管得住程序名，管不住参数；
4. **工单绝不自行宣布修好**：`Proposal.done` 恒 `False`。

**验证命令的口径**：跑该子系统的现有回归测试，**不是**「复现线上缺陷」。
绿 = 测试没覆盖这个缺陷（需补用例）；红 = 已有用例失败（直接拿到定位点）。
两者都真实可行动，且不假装跑一次 pytest 就等于复现了缺陷。

**质检结论由缺陷单直接给出**：计划书要求 Hook「联动质检 Agent」，
而缺陷单本身就是质检结论（再算一遍只会得到两份可能不一致的结论）。
安全 → `block`（Hook 直接拦，沙箱一次都不跑），其余 → `pass`。
没有这一步，`qa_link` 会因「未收到质检结论」把每张工单都判成待审批，闭环第一步就走不动。

**提案优先级**：显式 `harness_proposals`（决策层已判断）**优先于**缺陷单。
拿「发现」覆盖「判断」，等于把决定权从决策层夺走。

**本轮未实现（如实登记）**：补丁应用器。缺陷单 `diff` 为空且标注 `diff_pending`，
`requires_human_patch` 恒 True，Agent 输出 `patch_not_applied.applied=False`。
声称能自动改源码而实际没有，比不做更坏。

### 五、方法论限制（本节数字尤其要看）

- **同一批语料既用来发现问题、又用来验证修复**，存在过拟合风险。
  缓解是每处改动都落在**语言规则层**（限定语 vs 回忆指代、是非问句、
  显式连词、要素词），不是逐句加白名单；但没有第二套语料验证泛化能力，
  **79.0% 这个数不能当作线上准确率**。
- 62 句的置信区间仍是 ±6~8 个点，只能看排序与方向。
- 缺陷闭环的端到端验证用的是替身沙箱与构造报告；真实痕迹生产端仍未接线（§54.14 已登记）。

**装配断言**：`build_intent_router()` 是唯一装配点；`build_chat_orchestrator()`
在开关开着却没收到路由时**直接 ValueError** —— 静默退化比缺功能更坏。
守护测试还钉住三件事：装配出的层序列必须是 `LAYERS` 的子序列、L1 与 `classify()`
在同一条句子上同分类、影子态下 `evaluate` 必须立刻返回。

## 54.16 大模型写代码、机械层把关、评测中台复评（U78 / U79）

§54.15 末尾如实登记了一处未实现：**补丁应用器**。当时的闭环只到「变更单」，
`diff` 恒为空。本节把这一段接上，并且明确一条边界：

> 评测中台**判**，harness **改**，改完由评测中台**再判一次**。
> 改代码的一方不得给自己发结论。

### 一、三层分工，缺一层就不可控

| 层 | 模块 | 职责 | 不做什么 |
|---|---|---|---|
| 创作 | `harness/coder.py` | 向大模型要统一 diff | 不校验、不落盘、不宣布成功 |
| 机械 | `harness/patch.py` | 解析 / 范围校验 / 应用 / 回滚 | **不含任何智能**，不做模糊匹配 |
| 时序 | `harness/loop.py` | Hook → 应用 → 验证 → commit/rollback | 不判断补丁对不对 |

`CodeProposal` 里**没有也不会有**「已修复」字段。`ok=True` 只表示
「格式合法、范围合规、确有增删行」。

### 二、应用时序不可调换

```
Hook 判风险 → 应用补丁 → 跑验证命令 → 绿了 commit / 红了 rollback
```

- 先应用再判 Hook：高危变更先落地了才被拦；
- 先跑命令再应用：验的是**没改过的代码**，结论全部作废；
- 只应用不跑命令：未验证的改动，**回滚**。

`finally` 里兜底回滚，覆盖 Hook 拦截、审批暂停、无进展、上限归档，
以及决策层抛异常。「改了代码但循环异常退出」是留下半成品最容易的路径。

### 三、三条结构性防线（不依赖模型自觉）

| 防线 | 做法 | 挡的是什么 |
|---|---|---|
| 范围 | 按缺陷类别收窄到子系统 | 修检索召回却顺手动了调度器 |
| 禁区 | `tests/` 与 `ai_butler/evaluation/` 全局禁改 | **删断言 → 测试全绿而缺陷仍在**；被评方改判决书 |
| 规模 | 3 文件 / 200 行硬上限 | 「读不懂的自动变更」等于没审批 |

### 四、复评：两个判据互不替代

| 判据 | 看什么 | 要不要跑代码 | 不过就 |
|---|---|---|---|
| **没乱改**（`audit`） | diff 文本：越界 / 删断言 / 加 skip / 移除保护 / 规模 | 不用跑 | 直接打回，**连复跑都不跑** |
| **修好了**（复跑） | 同一批用例重跑：目标缺陷是否消失、有没有回归 | 必须真跑 | 打回并分类 |

结论是**四态 + 一个「不知道」**：`accepted` / `rejected_audit` /
`rejected_regression` / `rejected_no_effect` / `unverified`。没有布尔成功。

`unverified` 的三种来源都**不得**升级为 `accepted`：没有 `TraceProducer`
（无法重跑）、缺修复前基线（无从比较）、全部用例复评报错。
**「不知道」必须和「通过」分开**——拿「补丁已应用」推断「修好了」，
是本项目反复避免的假成功。

复评只从 harness 段取一样东西：**它想改的 diff**（作为审计对象）。
`converged` / `done` / `patch_applied` 一律不采信。

### 五、真机实测（云端 deepseek-chat，注入一个可判缺陷）

缺陷注入在 `planner.py` 的兜底分类：无确定性信号时返回 `SMALL_TALK`
而不是 `UNKNOWN`（`small_talk` 会跳过检索 —— 把「听不出来的问题」当闲聊，
等于不查就答）。

| 阶段 | 结果 |
|---|---|
| 第一轮评测 | `passed=False`，score 0.41，失败三维度（输出质量 / 检索召回 / 证据忠实） |
| 大模型创作 | 1 次成功，产出 2 行 diff，**精确改回 `UNKNOWN`** |
| 范围校验 + Hook | 通过（风险 low） |
| 沙箱验证 | `pytest tests/test_retrieval_planner.py` → exit=0 |
| harness 自评 | 收敛，2 轮，4.5s |
| **复评** | **`accepted`**，`fixed=('planner-unknown',)`，无回归，审计通过 |

### 六、三个真机踩到的坑（都已修）

**① 上下文给少了，模型会正确地拒绝。** 第一次跑，`planner.py` 529 行被切成
前 240 行，正好漏掉第 369 行的兜底分支。模型输出：

> `SKIP: 提供的源码片段在 PERSONAL_RECALL 信号处截断……无法在不臆造上下文的前提下产出可被接受的统一 diff`

**它做对了，是上下文给少了。** 修法：小文件整篇给（`FULL_FILE_CAP=700`），
并把 `SKIP` 记成**合法结局**而不是失败 —— 这是这条链路里最该奖励的行为。

**② 空补丁被当成产出。** 那次 `SKIP` 同时带了一个只有上下文行、没有 `+/-` 的
diff：语法合法，`touched=0`，一路走到 `apply` 才失败，白占一次 Hook 与沙箱预算。
修法：创作层直接拦 —— 解析成功不等于改动了代码。

**③ 复评在旧进程里跑，评的是旧代码。** 补丁落在磁盘，而模块对象在进程里是
已加载的缓存。第二次跑：补丁应用正确、测试全绿、循环收敛，**复评却报
`rejected_no_effect`**。看着像「改了半天没用」，实际是评错了对象。
这是本节的**最重要一条**：它会让所有复评稳定误判，而且指向完全错误的排查方向。

修法三层：`TraceProducer` 的契约里写死「须重载或重启」；`rejected_no_effect`
的理由里直接写出这条排查提示；`unverified` 作为「没把握时」的正确出口。

### 七、方法论限制

- 实证只有**一个**缺陷、一次修复。它证明链路**能**跑通，**不能**推出成功率；
- 注入的缺陷是「已知答案」的，模型的正确率高估了真实场景
  （真实缺陷的根因往往不在 evidence 里）；
- 复评的 `producer` 在实测里是「真调 `classify` 的包装」，不是完整对话管道
  （`chat.py` 的痕迹生产仍属未接线项，§54.14 已登记）；
- 沙箱是本机进程级，**没有容器隔离**（U34：容器由 AI Infra 提供）。

### 八、未实现（如实登记）

- 完整对话管道的痕迹生产端（`ChatOrchestrator` 运行时埋点）仍未接线；
- 补丁的「多轮协商」没有做：一次失败就 `rollback` 并在下一轮重来，
  不会基于失败信息自动改写补丁（模型只拿到创作阶段的格式/范围反馈，
  拿不到「测试红了」的反馈）；
- 安全缺陷的自动修复永久关闭（`manual` + 整批阻断），这是刻意的，不是待办。
